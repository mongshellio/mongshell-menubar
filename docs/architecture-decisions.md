## Decision 1: 자격증명 = Keychain 2단 폴백 (자체 OAuth → Claude Code CLI)

- **도입**: v1.0.0
- **컨텍스트**: 사용량 조회에는 구독 계정의 bearer 토큰이 필요하다. 그런데 주 사용자층(=만든 사람 본인 포함)은 이미 Claude Code 를 쓰고 있고, 그 토큰이 이 맥의 Keychain 에 이미 있다.
- **결정**: 읽기 우선순위를 (1) 자체 OAuth 토큰 → (2) Claude Code CLI 토큰(Keychain `Claude Code-credentials`, 없으면 `~/.claude/.credentials.json`) 으로 둔다. 자체 토큰이 없으면 로그인을 요구하지 않고 CLI 토큰을 재사용한다.
- **이유**: 앱을 켜자마자 실데이터가 보이는 것이 이 프로덕트의 첫인상 전부다. 로그인 화면을 한 번 거치게 하면 "메뉴바에 띄우기만 하면 되는 앱" 이라는 기대와 어긋난다.
- **결과**: Claude Code 사용자는 로그인 0회로 시작한다. 대신 **다른 앱의 Keychain 항목을 읽으므로 첫 실행 시 "키체인 접근 허용" 프롬프트**가 뜨고, 이걸 설치 안내에 명시해야 한다.
- **트레이드오프**: App Sandbox 를 쓸 수 없다 (Decision 3 과 함께 App Store 배포를 배제한다). ad-hoc 서명은 빌드마다 서명이 바뀌어 Keychain 접근 승인이 초기화된다.

## Decision 2: 비공식 사용량 엔드포인트 + Claude Code OAuth client 재사용

- **도입**: v1.0.0
- **컨텍스트**: Claude **구독(Pro/Max) 한도에는 공식 API 가 없다.** 공식 API 키는 종량 과금 API 사용량을 말하는 것이라 이 앱이 보여주려는 숫자와 다르다.
- **결정**: `GET https://api.anthropic.com/api/oauth/usage` 를 쓴다. OAuth 는 Claude Code 의 client_id 와 `User-Agent: claude-code/<version>` 을 그대로 쓴다.
- **이유**: 대안이 없다. Anthropic 은 서드파티에 client_id 를 발급하지 않는다. 값들은 커뮤니티 리버스엔지니어링으로 확인된 실제 값이다.
- **결과**:
  - **ToS 회색지대**(공식 클라이언트 사칭 성격)임을 README 와 코드 주석에 명시한 채로 간다. 숨기지 않는 것이 이 결정의 일부다.
  - 응답 스키마가 비공개라 `UsageAPIClient.parse()` 는 후보 키 경로를 여러 개 탐색하고 채울 수 있는 것만 채우는 **관대한 디코딩**을 한다. 스키마가 바뀌어도 앱이 죽지 않고 일부 필드만 비는 것을 정상 동작으로 둔다.
  - `User-Agent` 가 빠지면 공격적인 rate limit 버킷으로 떨어져 지속적인 429 를 받는다 — 이 헤더는 선택이 아니라 필수다.
  - 토큰·로그인이 없으면 UI 는 샘플 데이터로 렌더한다 (빈 화면 대신).
- **폐기 조건**: 엔드포인트가 막히면 이 앱은 기능하지 않는다. 대체 경로를 미리 만들지 않는다 — 만들 수 있는 게 없다.

## Decision 3: 배포 이원화 — ad-hoc 로컬 빌드 기본, Developer ID 공증은 선택

- **도입**: v1.0.0
- **컨텍스트**: Apple Developer 계정은 연 $99 다. 이 앱은 1인용으로 시작했고, ToS 회색지대라 App Store 심사 대상도 아니다.
- **결정**: 기본 배포 경로는 **"각자 클론해서 `scripts/make_app.sh` 로 빌드"** 다 (ad-hoc 서명 — 직접 빌드한 앱은 Gatekeeper 가 막지 않는다). 서명·공증된 `.dmg` 는 `scripts/release.sh` 라는 **별도 선택 경로**로 둔다.
- **이유**: 유료 계정 없이도 앱이 완전히 동작해야 하고, 유료 계정이 있는 사람만 지인 배포를 열 수 있으면 된다.
- **결과**:
  - README 의 설치 안내가 "빌드하세요" 로 시작한다. 진입 장벽이지만 대상 사용자(개발자)에겐 수용 가능하다.
  - ad-hoc 은 빌드마다 서명이 바뀌므로 **업데이트할 때마다 Keychain 재승인·재로그인**이 필요하다. Developer ID 로 서명하면 토큰이 유지된다 — 이것이 유료 경로의 실질 이득이다.
  - App Sandbox 를 쓰지 않는 것과 결합해 App Store 배포는 범위 밖이다 ([PHILOSOPHY.md](PHILOSOPHY.md) § Out of Scope).

## Decision #3: 메뉴바를 단일 Claude 마크 + 5h/7d 동시 표시로

- **도입**: v1.0.0 (#3)
- **컨텍스트**: 초기 버전은 아이콘 컨셉 6종(햄스터 등)을 설정으로 고르게 하고, 메뉴바에는 **하나의 지표만** 골라 표시했다.
- **결정**: 아이콘 선택지를 전부 제거하고 Canvas 로 그린 Claude 테라코타 스타버스트 마크 하나로 고정한다. 메뉴바에는 5시간·7일 **두 지표를 동시에** 표시한다.
- **이유**: "지금 여유가 있는가" 는 두 한도를 함께 봐야 답할 수 있는 질문이다. 하나만 보여주고 나머지를 클릭 뒤에 숨기면 글랜스가 성립하지 않는다. 아이콘 6종은 취향 옵션이었지 글랜스 품질에 기여하지 않았다.
- **결과**: `Preferences` 에서 `iconConcept`·`menuBarMetric` 이 사라져 설정이 단순해졌다. 메뉴바 폭이 늘어난 것이 대가였고, 이는 #5 에서 링 게이지로 컴팩트화하며 회수했다.
- **파생**: 5시간 창은 리셋 시각을 놓치기 쉬워 **5h 에만 초기화 시각을 함께** 표시한다. 주간 리셋은 기억하기 쉬워 팝오버로 미룬다.

## Decision #4: openclaw 통합을 완전 선택 기능으로

- **도입**: v1.0.0 (#4)
- **컨텍스트**: 로컬 openclaw 게이트웨이의 건강 상태도 글랜스로 알면 좋지만, 이 앱 사용자 대부분은 openclaw 를 쓰지 않는다.
- **결정**: openclaw 관련 UI 는 **CLI 가 설치돼 있고 사용자가 `Claude + openclaw` 를 고른 경우에만** 존재한다. 그 외에는 메뉴바·팝오버·설정 어디에도 나타나지 않는다 — 비활성 상태로 회색 표시하지도 않는다.
- **이유**: [PHILOSOPHY.md](PHILOSOPHY.md) § Design Principles 2 — 전제가 없으면 흔적도 남기지 않는다. "회색으로 비활성" 도 글랜스를 방해하는 시각적 소음이다.
- **결정 세부**: 상태 판정은 포트/HTTP 체크가 아니라 `openclaw channels status --probe` 파싱이다. 게이트웨이는 살아 있어도 채널 워커만 죽은 상태(🟡)를 포트 체크로는 잡을 수 없기 때문이다.
- **결과**: 새 외부 의존성 없이 Foundation `Process` 만 쓴다. 셸아웃은 `OpenClawService` 에 격리하고 타임아웃·백그라운드 실행으로 메인 스레드를 막지 않는다. 자동복구(2회 연속 실패 + 쿨다운 600초 → `launchctl` 하드 재시작)를 붙였다.
- **동반 변경**: 앱 이름을 Quota → mongshell-menubar 로, 번들 ID 를 `com.quota.app` → `com.mongshell.menubar` 로 바꿨다 (Keychain 서비스·URL scheme 동반 변경). Claude Code 의 Keychain 항목 이름과 Claude 브랜드 문자열은 그대로 둔다 — 그건 우리 것이 아니다.

## Decision #5: openclaw 를 두 번째 status item 이 아닌 단일 아이템에 일원화

- **도입**: v1.0.0 (#5)
- **컨텍스트**: #4 는 openclaw 를 **별도의 두 번째 `NSStatusItem`** 으로 붙였다. 메뉴바에 이 앱의 아이콘이 두 개가 됐다.
- **결정**: 두 번째 status item 과 전용 팝오버(`OpenClawStatusView`/`OpenClawPopoverView`)를 제거하고, 기존 사용량 아이템·팝오버 안으로 통합한다 — 메뉴바에는 사용률 오른쪽에 발자국 + 신호등 점, 팝오버에는 주간 섹션 아래 openclaw 섹션.
- **이유**: 메뉴바 공간은 이 앱만 쓰는 게 아니다. 한 앱이 두 칸을 차지하는 것은 1인 사용자 기준으로도 과하다.
- **동반 결정 (메뉴바 컴팩트화)**: 텍스트 `5h NN% · 7d NN%` 를 작은 **링 게이지 2개**로 바꿨다. 정확한 %와 7d 리셋 시각은 팝오버로 미루고, 메뉴바에는 5h 초기화 시각만 남긴다. 바 폭이 크게 줄었다.
- **결과**: `AppDelegate` 에서 두 번째 status item 로직이 사라졌다. 정확한 숫자를 보려면 클릭이 필요해졌다 — 글랜스는 "여유가 있는가" 까지만 답하면 된다는 판단.

## Decision #8: hover 요약을 네이티브 툴팁이 아닌 커스텀 팝오버로

- **도입**: v1.0.0 (#8)
- **컨텍스트**: #5 로 메뉴바에서 정확한 % 가 사라진 뒤, 클릭보다 가벼운 확인 수단으로 hover 툴팁(#7)을 붙였다. 그런데 macOS 네이티브 툴팁은 **표시까지 약 1초** 걸린다.
- **결정**: 네이티브 툴팁을 버리고 `NSTrackingArea` 로 hover 를 직접 감지해 SwiftUI `HoverSummaryView` 팝오버를 **즉시** 띄운다. 클릭 팝오버와는 상호배타로 동작한다(클릭 시 hover 팝오버를 먼저 닫는다).
- **이유**: 1초 지연은 "흘긋 보기" 를 성립시키지 못한다. 그 지연을 없애는 것이 이 기능의 존재 이유 전부였다.
- **결과**: 툴팁 문자열을 수동으로 재계산할 필요가 사라졌다 — SwiftUI 뷰라 스냅샷 갱신·표시 모드 토글에 자동으로 따라온다. 대신 hover/클릭 팝오버의 생명주기를 `AppDelegate` 가 직접 관리한다.
- **후속 (#9)**: 라벨/퍼센트 너비가 행마다 달라 `HStack` 에서 열이 어긋났다. `Grid`/`GridRow` 3열(라벨 · 퍼센트 우측정렬 · 초기화)로 교체.
- **후속 (#33)**: hover 팝오버가 `.transient` 라 AppKit 이 아이콘 클릭을 "바깥 클릭" 으로 보고 요약만 닫은 뒤 그 클릭을 삼켰다 — 버튼 동작이 호출되지 않아 클릭 팝오버는 두 번째 클릭에야 열렸고, 위 결정의 "클릭 시 hover 팝오버를 먼저 닫는다" 가 뜻한 한 번 클릭이 성립하지 않았다. `.applicationDefined` 로 바꿔 클릭이 버튼에 닿게 하고, `.transient` 가 맡던 정리 중 "커서는 떠났는데 닫힘 이벤트를 놓친 경우" 는 요약이 떠 있는 동안의 커서 위치 감시로 대신한다. 포기한 것: 커서가 아이콘 위에 머문 채 앱을 전환하면 요약은 이제 남는다.
- **후속 (#34)**: hover 요약을 메뉴바 버튼에 붙여 띄우면 마우스만 올려도 항목 배경이 선택된 것처럼 바뀌었다(다른 앱은 hover 에 반응하지 않는다). 요약을 버튼 위에 겹친 투명·click-through 보조 창에 붙여 띄운다 — 버튼에 붙은 팝오버가 그 강조의 원인이라는 추정에 따른 것이고, 강조는 시스템이 그려 API 로 확인되지 않아 실기 확인으로 검증한다. 클릭 팝오버는 버튼에 그대로 붙어 선택 표시가 유지된다. 포기한 것: 요약의 위치는 버튼을 직접 따라가지 않고, 떠 있는 동안 0.5초 간격으로 맞춘다.
- **후속 (#36)**: #35 에서 클릭 팝오버도 보조 창에 붙여 열려 있는 동안의 강조를 없앴으나, 실기에서 바깥 클릭으로 닫히지 않고 여는 데 두 번 눌러야 했다 — 버튼에 붙은 `.transient` 팝오버에 AppKit 이 해 주던 열기·닫기 동작이 보조 창에서는 성립하지 않았다. #35 를 되돌린다. #34 의 추정(버튼에 붙은 팝오버가 강조의 원인)은 실기로 확인됐고 hover 쪽은 그대로 둔다. 클릭 팝오버는 버튼에 붙어 있고, 열려 있는 동안의 강조는 남는다.
- **후속 (#39)**: 클릭 팝오버를 자체 창으로 띄워 강조를 없애는 시도(#37, Stats 앱과 같은 구조)와 그 보정(#38)을 되돌린다. 강조는 사라졌지만 열린 상태에서 아이콘을 누를 때 닫혔다 다시 열리는 문제와 그 보정 뒤의 깜빡임이 남았고, 강조가 남는 쪽이 낫다고 판단했다. **클릭 팝오버는 버튼에 붙은 `NSPopover` 로 두고, 열려 있는 동안의 강조는 받아들인다** — 강조를 없애려면 시스템 팝오버가 해 주는 열기·닫기를 전부 직접 만들어야 하고(#35·#37·#38 세 번의 시도가 모두 실기에서 어긋났다), 이 앱에서는 그 값을 치르지 않는다. hover 요약의 무강조(#34)와 첫 클릭 열림(#33)은 유지한다.
- **후속 (#70)**: 클릭 팝오버의 더보기(⋯) 메뉴가 뜨자마자 닫히고, 그 뒤 팝오버가 바깥 클릭으로 닫히지 않았다. 상태 아이템 클릭으로는 앱이 활성화되지 않아, 팝오버 안 첫 클릭 때 뒤늦게 일어나는 앱 활성화가 막 열린 메뉴를 닫았다. 또 메뉴가 떠 있는 동안 앱이 비활성화되면 AppKit 은 `.transient` 팝오버의 닫기를 보류한 채 메뉴가 닫힌 뒤 다시 판정하지 않았다 (진단 로그로 확인). 팝오버를 띄우기 직전 `activate(ignoringOtherApps:)` 로 앱을 활성화하고, 앱이 비활성화되면 클릭 팝오버를 직접 닫는다. `NSApp.activate()`·`NSRunningApplication.activate`·비활성화 패널은 실기에서 메뉴를 살리지 못했다. 포기한 것: 팝오버를 열면 쓰던 앱의 키보드 포커스를 이 앱이 가져가고, 팝오버를 아이콘이나 메뉴 항목으로 닫으면 포커스가 저절로 돌아가지 않는다.

## Decision #11: `~/.claude/settings.json` 편집은 read-modify-write

- **도입**: v1.1.0 (#11)
- **컨텍스트**: 설정창에서 Claude Code 설정 5개 키(기본 모델·추론 강도·대체 모델·컨텍스트 자동 압축·권한 기본 모드)를 편집한다. 이 파일은 **CLI 와 공유하는 사용자의 실제 설정**이고, 권한 규칙·플러그인 설정·hooks 처럼 앱이 모르는 키가 들어 있다.
- **결정**: 저장은 인메모리 스냅샷을 통째로 쓰지 않는다. **저장 직전 디스크에서 다시 읽고, 사용자가 방금 건드린 키 하나만 반영**한다(`applyChange`). 읽기에 실패하면 **쓰지 않는다.**
- **이유**: 인메모리 스냅샷으로 5개 키를 전부 다시 쓰면, 파일 감시가 외부 변경을 놓친 구간에서 무관한 토글 하나를 누르는 것만으로 방금 CLI 로 바꾼 `permissions.defaultMode` — 도구 실행 승인 게이트다 — 가 조용히 되돌아간다. 읽기 실패를 빈 파일로 강등하면 다음 저장이 파일 전체를 날린다.
- **결과 / 파생 규칙**:
  - 타입이 예상과 다른 값은 "사용자가 비웠다" 로 보지 않고 그대로 둔다.
  - UI 슬롯이 2개인 `fallbackModel` 이 파일에 3개 있으면 화면에 없는 3번째를 보존한다.
  - 쓰기 직전 `lstat` 으로 심링크를 확인하고 거부한다 — dotfile 관리 도구가 재stow 중이면 원자적 쓰기가 링크를 일반 파일로 갈아치운다.
  - 백업(`settings.json.bak`) 권한 0600, 5MB 상한, 파일 감시 이벤트 150ms 디바운스.
  - 기본값으로 되돌리면 값을 쓰는 대신 **키를 삭제**한다.
  - 의미는 보존되지만 **표기는 정규화**된다(중복 제거, 기본값을 명시한 키 삭제, 키 정렬). 손으로 잡아둔 순서·들여쓰기는 유지되지 않는다.
- **범위 밖**: `hooks`·`env`·MCP 같은 자유형 키는 다루지 않는다. 권한 기본 모드에서 `allow`(전부 허용)는 GUI 오조작 위험 때문에 선택지에서 뺐다 — 파일에 이미 있으면 "직접 설정한 값" 으로 보여주고 유지한다.

## Decision #11-1: 테스트는 `swift test` 가 아니라 실제 소스 직접 컴파일

- **도입**: v1.1.0 (#11)
- **컨텍스트**: Decision #11 의 불변식("보이지 않는 설정을 앱이 파괴하지 않는다")은 회귀 테스트 없이 지킬 수 없다. 그런데 `swift test` 는 XCTest 나 swift-testing 을 요구하고, **둘 다 Command Line Tools 에 들어 있지 않다.** "Xcode 없이 빌드 가능" 은 Decision 3 이 세운 전제다.
- **결정**: SwiftPM 테스트 타깃을 만들지 않는다. `scripts/test.sh` 가 `swiftc` 로 **실제 소스 파일과 테스트 파일을 함께 컴파일**해 실행한다.
- **이유**: 테스트 프레임워크를 위해 Xcode 필수라는 전제를 들이는 것보다, 테스트 러너를 포기하는 쪽이 싸다. 부수 효과로 테스트가 사본이 아니라 **배포되는 코드 그대로**를 검증한다.
- **결과**:
  - `Package.swift` 에 test 타깃이 없는 것이 정상이다 — 없다고 추가하면 CLT 환경 빌드가 깨진다. 그 이유를 `Package.swift` 주석에 남겨 뒀다.
  - 새 테스트 대상을 추가할 때 **의존 소스 파일을 `scripts/test.sh` 에 직접 나열**해야 한다. 자동 탐색이 없다 — 이것이 이 선택의 유지보수 비용이다.
  - 테스트가 실제 `~/.claude/settings.json` 을 건드리지 못하도록 실행 직전 `env -u MONGSHELL_CLAUDE_SETTINGS` 로 상속된 값을 지운다.

## Decision #11-2: 뷰 로컬 상태는 `@State` 매크로 대신 `State<Value>` 수동 펼침

- **도입**: v1.2.0 (#24)
- **컨텍스트**: Command Line Tools 27.0 (2026-09) 은 macOS 27 SDK 를 기본으로 쓰고, 이 SDK 에서 `@State` 는 프로퍼티 래퍼가 아니라 `SwiftUIMacros` 플러그인이 전개하는 **매크로**가 됐다. 그 플러그인은 Xcode 에만 동봉되고 CLT 에는 없어서 `@State` 가 한 줄만 있어도 CLT 빌드가 실패한다. "Xcode 없이 빌드 가능" 은 Decision 3 / #11-1 이 세운 전제다.
- **결정**: `@State` 를 쓰지 않는다. `State<Value>` 프로퍼티 래퍼 타입은 SDK 에 그대로 남아 있으므로, 매크로가 만들었을 저장 프로퍼티(`_x = State(initialValue:)`)와 접근자(`wrappedValue` get / nonmutating set)를 직접 적는다.
- **이유**: 대안은 셋이었다. (a) 스크립트에서 이전 SDK(26.5) 를 고정 — 다음 CLT 업데이트에서 그 SDK 가 빠지면 도리어 설치 부담이 생긴다. (b) Xcode 설치 요구 — 전제를 깬다. (c) 수동 펼침 — 의미가 `@State` 와 동일하고 수정 범위가 뷰 한 곳이라 가장 싸다. `@StateObject` + `ObservableObject` 로 바꾸는 것도 되지만 생명주기 의미가 달라져 동작 보존이 아니다.
- **결과**:
  - `@Binding`·`@ObservedObject`·`@StateObject`·`@Environment`·`@AppStorage` 는 27 SDK 에서도 프로퍼티 래퍼라 그대로 쓴다. `@Entry`·`@Animatable` 은 같은 플러그인을 요구하므로 쓰지 않는다.
  - Apple 이 CLT 에 플러그인을 동봉하면 이 결정은 철회 가능하다 — 그때 `@State` 로 되돌리는 것은 순수 리팩토링이다.

## Decision #25: openclaw 감시를 원격 서버 에이전트 + Funnel 정적 상태 파일로

- **도입**: v1.2.0 (#25)
- **컨텍스트**: openclaw 가 메뉴바 앱을 쓰는 맥북이 아니라 24시간 도는 별도 서버 맥으로 옮겨갔다. 맥북은 여러 대이고 서버와 다른 네트워크에 있으며, 포트포워딩은 하지 않고 클라이언트에 Tailscale 을 설치하지 않는다. #4 의 로컬 셸아웃은 전제 자체가 사라졌다.
- **결정**: 로컬 모드를 완전히 제거한다. 서버 맥에서 이 repo 의 `mongshell-openclaw-agent`(LaunchAgent)가 `openclaw channels status --probe` 를 판정하고 자동복구를 수행한 뒤, 판정 결과를 JSON 파일로 쓴다. 오픈소스판 Tailscale 의 `tailscale funnel --https=8443 --set-path /<토큰> <파일>` 이 그 파일을 **공개 전용 포트 8443** 에 공개하고, 메뉴바 앱은 그 URL 을 HTTPS 로 읽기만 한다.
- **이유**:
  - 판정을 서버에 두는 이유 — 자동복구가 서버에 있으므로 판정도 거기 있어야 하고, 원시 출력을 보내 클라이언트가 다시 파싱하면 파서가 두 벌이 된다.
  - 파일 서빙을 택한 이유 — 우리 코드에 인터넷에 노출되는 리스너가 없다. 쓰기 동작이 구조적으로 불가능하고, 주소 한 줄(capability URL)로 설정이 끝난다.
  - 공개 전용 포트 8443 인 이유 — funnel 은 경로가 아니라 포트(host:port) 단위로 공개한다. 443 에 tailnet 전용으로 둔 기존 serve 핸들러가 있으면 우리 경로를 켜는 순간 함께 노출되므로 포트를 분리하고, 설치 스크립트는 8443 에 우리 것 외 핸들러가 있으면 중단한다.
  - 공개 detail 에 허용 문자 필터를 두는 이유 — 채널 이름은 openclaw 출력에서 잘라 온 외부 문자열이라 봇 계정명·토큰 조각이 섞일 수 있고, URL 은 토큰 하나로만 보호된다. 그래서 영문·한글·숫자·` ._-` 로 된 32자 이하 이름만 그대로 싣고 나머지는 "채널 N개" 로 요약한다. 판정(ok/degraded/down)은 필터 이전에 정해진다.
  - Swift 에이전트를 택한 이유 — 채널 워커만 죽은 상태를 잡는 판정 규칙(#4 결정 세부 승계 — 포트/HTTP 체크가 아니라 probe 파싱)을 bash 로 다시 짜면 테스트할 수 없고, macOS 에는 `timeout` 이 없다.
- **결과**:
  - 표시 규칙 — #4 의 "CLI 가 설치돼 있을 때만" 은 "상태 URL 이 설정돼 있고 `Claude + openclaw` 를 골랐을 때만" 으로 바뀐다. 원격 전제는 이 맥에서 감지할 수 없으므로 상태 URL 입력칸에 PHILOSOPHY 원칙 2 의 설정 진입점 예외를 적용해 URL 이 없어도 보이게 하고, 그 밖의 openclaw 요소는 URL 이 적용된 뒤에만 나타난다.
  - 상태 — `.unreachable`(회색) 추가, 판정 기준은 마지막 성공 응답의 `checkedAt` 이 `max(180초, 3×interval)` 을 넘었는가 하나. 빨강은 서버가 게이트웨이 다운을 보고했을 때만 — 클라이언트 오프라인 오경보 방지.
  - 팝오버의 재시작·PID·대시보드·로그 제거. 공개 URL 로 쓰기 동작을 열지 않는다.
  - 자동복구 설정은 서버 설치 스크립트 플래그(기본 켬)로 옮기고, 앱은 `lastHeal` 변화 알림만 한다.
  - 상태 URL 은 Preferences(UserDefaults) — 읽기 전용이고 `--rotate-token` 으로 폐기 가능하다. Keychain 규칙은 Claude 자격증명 대상이다.
  - 에이전트는 자기 자신을 kickstart 하지 않도록 게이트웨이 레이블을 설치 시 고정하고, 탐색에서 자기 레이블을 빼며, 명시 레이블이 자기 레이블이면 무시한다.
  - 옛 토큰 경로 해제(`--rotate-token`·uninstall)는 fail-closed 다 — 해제 후 serve 설정에 남아 있으면 중단한다.
  - **단계적 적용 (완료)**: 서버 에이전트·설치 스크립트를 먼저 들이고, 이어서 앱 측을 교체했다 — 원격 URL 읽기(`OpenClawStatusClient`), `.unreachable`, 로컬 셸아웃(`OpenClawService`)과 팝오버 쓰기 동작 제거. 판정 규칙은 이제 에이전트 `Probe` 한 벌뿐이고, 앱은 JSON 을 읽어 표시만 한다. 두 타깃의 JSON 키 정합은 `Tests/OpenClawClientTests` 의 왕복 케이스(에이전트 인코더 → 앱 파서)가 지킨다.
- **후속 (#42)**: probe 실행과 판정에서 두 가지 사고가 실측됐다. (1) openclaw 진입점은 자기 자신을 stdio 상속으로 다시 띄우므로 실제 작업 프로세스는 손자다. 직접 띄운 자식만 죽이면 손자가 파이프를 쥔 채 남고, 그 뒤의 블로킹 읽기가 손자가 끝날 때까지 멈춰 에이전트가 통째로 정지할 수 있었다(살아 있는 프로세스라 KeepAlive 도 손대지 않는다). (2) fd 고갈로 출력을 못 받았을 때 빈 출력을 `down` 으로 판정해 정상 게이트웨이를 쿨다운마다 재시작했다. 그래서 — probe 는 새 프로세스 그룹으로 띄워 시간 초과 시 그룹째 끝내고, 자식이 스스로 끝난 뒤 그룹에 남은 프로세스도 정리한다. 출력은 마감(시간 초과 + 1초 유예 + 1초)까지만, 자식이 먼저 끝났으면 그 뒤 1초까지만 읽는다 — 그룹을 빠져나간 자손이 파이프를 쥐어도 거기서 끊는다. 실행 실패·빈 출력은 판정이 아니라 **관측 실패**로 분리해 상태 파일에 싣지 않고 복구 카운트에도 넣지 않는다. 관측 실패 뒤에는 그 자리에서 재시도하지 않고 주기만큼 기다린 뒤 종료해 launchd 가 새 프로세스를 띄우게 한다 — 원인이 에이전트 프로세스 안(fd 고갈 등)에 있을 가능성이 크고, 새 프로세스가 그것을 가장 확실히 털어낸다. 포기한 것: 관측 실패가 이어지는 동안 상태 파일이 갱신되지 않아 맥북에는 빨강이 아니라 회색(연락 두절)으로 보이고, 원인은 서버 로그를 봐야 안다. 비어 있지 않은 에러 문구를 내며 끝나는 경우는 여전히 기존 규칙대로 판정한다. 출력 없이 신호로 죽은 probe 도 관측 실패로 둔다(openclaw 는 손자가 신호로 죽으면 같은 신호로 자기 자신을 죽인다) — 일꾼이 매번 그렇게 죽으면 에이전트는 재기동만 반복하고 자동복구는 하지 않는다. 게이트웨이 재시작으로 고쳐지지 않는 CLI 쪽 문제라고 판단했고, 원인은 로그의 신호 번호로 남긴다.
- **트레이드오프**: 서버에 오픈소스판 Tailscale(brew) 필요, 서버에서 CLT 빌드, 재부팅 후 자동 로그인 필요, 토큰이 경로에 있어 헤더보다 위생이 낮음, 외부 의존에 Tailscale Funnel 추가, 비표준 포트(8443)라 443 만 허용하는 네트워크에서는 읽을 수 없음.
- **폐기 조건**: 서버가 App Store/Standalone 판 Tailscale 을 써야 하게 되면, 에이전트에 헤더 토큰 HTTP 리스너를 붙이고 포트 프록시로 전환한다.

## Decision #31: 상태 문서에 서버 호스트 신호(전원·디스크)를 추가

- **도입**: v1.2.0 (#31)
- **컨텍스트**: #25 로 openclaw 게이트웨이의 건강은 메뉴바에서 보이게 됐지만, 서버 맥 자체가 곧 멈출 조짐(어댑터가 빠짐, 디스크가 참)은 여전히 접속해서 봐야 알았다. 게이트웨이가 정상이어도 서버가 배터리로 돌고 있으면 몇 시간 뒤 함께 죽는다. [PHILOSOPHY.md](PHILOSOPHY.md) § Admission Criteria 가 이런 신호의 입장 기준으로 신설됐고, 전원과 디스크 여유가 5개 기준을 통과했다.
- **결정**: #25 의 상태 문서에 최상위 `host` 객체를 추가한다. 에이전트가 IOKit 전원 정보와 홈 볼륨의 여유 공간을 읽어 신호별(`power.health`, `disk.health`)·종합(`host.health`) 판정을 `ok` / `warning` / `critical` 로 내리고, 판정과 함께 표시에 쓰는 상태값(불리언 `pluggedIn` · `charging`, 수치 `batteryPercent` · `availableBytes`)만 싣는다. 앱은 읽어서 표시하고 알릴 뿐이다. 메뉴바에는 openclaw 표시 아래에 서버 글리프 + 점을 쌓고, 팝오버에는 openclaw 섹션 아래 서버 섹션을 둔다. 두 점은 서로 독립이다 — 게이트웨이가 다운이어도 서버가 멀쩡하면 빨강 아래 초록이다.
- **판정 규칙** (에이전트 `HostRules` 한 벌):
  - 전원 — 어댑터 연결이면 잔량과 무관하게 ok. 배터리 구동이면 warning, 잔량 20% 이하면 critical. 배터리 구동인데 잔량을 읽지 못하면 warning 에 머문다. 내장 배터리가 없거나 전원 공급원을 알 수 없으면 신호 자체가 없다. 시스템이 공급원을 말해 주지 않을 때는 배터리 자신의 상태가 `AC Power` / `Battery Power` 일 때만 그것으로 판단하고, 그 밖의 값(`Off Line` 등)은 "알 수 없음" 이다 — 재지 않은 ok 를 싣지 않는다.
  - "어댑터 연결"(`pluggedIn`)의 정의 — 시스템 전원 공급원이 내장 배터리가 **아님**. 내장 배터리가 있는 맥이 UPS 전원으로 도는 경우도 연결로 본다.
  - 디스크 — 홈 볼륨 여유가 20GB 미만이면 warning, 5GB 미만이면 critical. GB 는 10진(10⁹ 바이트)이다.
  - 종합 — 있는 신호 중 가장 나쁜 것. 신호가 하나도 없으면 `host` 는 `null` 이다.
  - 히스테리시스는 없다. 임계 위에 걸친 값은 probe 마다 레벨이 오갈 수 있고, 그 출렁임은 앱의 알림 쿨다운이 받는다.
- **이유**:
  - 판정을 에이전트에 두는 이유 — #25 와 같다. 앱이 수치로 다시 판정하면 임계값이 두 벌이 된다. 신호별 판정을 함께 보내므로 앱은 임계값을 몰라도 원인을 짚을 수 있고, 종합 판정을 따로 보내므로 앱이 모르는 신호가 생겨도 점 색은 맞는다.
  - `schema` 를 올리지 않는 이유 — 키 추가는 기존 클라이언트를 깨뜨리지 않는다. `schema` 는 기존 키의 의미가 바뀌거나 키가 사라질 때만 올린다.
  - 어댑터 연결 중 낮은 잔량이 경고가 아닌 이유 — 할 일이 없다. 행동을 부르지 않는 상태는 경고가 아니다 (Admission Criteria 2).
  - 디스크 임계가 비율이 아니라 절대값인 이유 — 서버를 멈추는 것은 남은 절대 공간이다. 큰 디스크의 95% 사용은 문제가 아니다.
  - 아래로 쌓는 이유 — Admission Criteria 4 는 메뉴바 가로 폭을 늘리지 않을 것을 요구한다. 세로 스택은 그 기준을 만족시키려고 이 결정이 고른 수단이다: 서버 점을 openclaw 표시 옆이 아니라 아래에 두면 폭이 늘지 않고, 그래서 원칙 1 의 "무엇을 뺄지" 요구 없이 들어온다. 두 줄이 22pt 메뉴바에 들어가도록 스택일 때는 글리프와 점을 단일 표시보다 작게 그린다.
  - `totalBytes` 를 싣지 않는 이유 — 표시에 쓰지 않는 값으로 공개 표면을 늘리지 않는다. 디스크 판정이 절대값이라 전체 용량은 판정에도 표시에도 쓰이지 않는다.
  - 앱이 모르는 레벨 문자열을 `warning` 으로 읽는 이유 — 에이전트가 무언가를 판정했다는 뜻이므로 초록으로 칠하면 안 된다. 문자열이 아닌 `health` 값(수·객체 등)과 판정이 빠진 신호도 같은 이유로 `warning` 이다.
  - 쿨다운에 눌린 상승을 버리지 않고 미루는 이유 — 쿨다운은 출렁임을 막는 장치이지 상태를 숨기는 장치가 아니다. 버리면 "알림 → 회복 → 다시 나빠져 그대로 머묾" 이 끝내 알려지지 않는다.
  - 전원 문구에서 원인을 조건부로만 말하는 이유 — 전원 레벨은 앱이 판정을 읽지 못해 `warning` 으로 접은 것일 수도 있다. 그때 "어댑터 분리" 라고 하면 같은 화면의 "충전 중" 과 모순된다.
- **결과**:
  - 표시 조건 — `Preferences.showsOpenClaw` 가 참이고 서버가 `host` 를 보낼 때만 나타난다. 구버전 에이전트의 서버 점·섹션, 배터리 없는 서버의 전원 줄은 자리 없이 사라진다 (원칙 2). 별도 설정 토글은 없다.
  - 라벨 — 표시 대상 선택지 `Claude + openclaw` 는 `Claude + 서버` 로, 설정 섹션 제목 `openclaw` 는 `서버` 로 바뀐다 (#4·#25 본문의 옛 라벨은 이 선택지를 가리킨다). 저장값(`MenuBarTarget.claudeAndOpenClaw` 의 rawValue)은 그대로라 기존 설정이 유지된다. 타입·타깃 이름은 바꾸지 않는다 (아래 트레이드오프).
  - 연락 두절(회색) 판정은 #25 의 신선도 규칙을 그대로 공유한다. 두절 중에는 마지막으로 받은 값을 흐리게 남긴다 — 두절의 원인(배터리 소진)을 짐작하게 해 준다. 마지막 성공 응답에 `host` 가 없었거나 성공 응답이 아직 없으면 회색 점도 그리지 않는다.
  - 관대한 읽기 — `host` 가 어떻게 깨져 있어도 잃는 것은 서버 점뿐이고 openclaw 판정은 그대로 읽는다. `host.health` 가 없거나 `null` 이면 신호 중 가장 나쁜 것이 종합을 대신한다. 값이 있는데 읽을 수 없으면(모르는 문자열, 문자열이 아닌 값) 폴백하지 않고 `warning` 이다. `availableBytes` 를 쓸 수 없으면 디스크 신호는 없는 것으로 본다.
  - 표시 문구 — 전원의 원인 문구(상태어 "어댑터 분리"·"배터리 부족", 알림의 어댑터·배터리 문구)는 문서가 `pluggedIn: false` 라고 말할 때만 쓴다. `true` 이거나 알 수 없으면 레벨만 말한다 (상태어 "전원 주의"·"전원 위험", 알림은 같은 제목에 받은 수치만).
  - 알림 — 신호별로 레벨이 오를 때 알린다. 앱 시작(또는 상태 URL 변경) 뒤 첫 응답은 기준점이다. 기준점에 없던 신호가 나중에 처음 나타나면 ok 에서 오른 것으로 본다. 이미 알린 레벨 이하로 다시 오르는 것은 마지막 알림에서 1시간(쿨다운)이 지나야 알리고, 그보다 높은 레벨로의 상승은 즉시 알린다. 쿨다운에 눌린 상승은 버리지 않고 미룬다 — 쿨다운이 끝난 뒤 첫 관측에서 그 신호가 여전히 ok 보다 나쁘면 그때의 레벨로 한 번 알리고, 그 사이 ok 로 회복했으면 알리지 않는다. 그 밖에 같은 레벨에 머무는 동안에는 다시 알리지 않는다. 회복과 두절은 알리지 않는다. 쿨다운은 맥북의 시계로 재며, 시계가 마지막 알림보다 앞으로 되돌려졌으면 쿨다운이 끝난 것으로 본다.
  - 통지 게이트가 닫힌 상태(`Claude만` 선택, 또는 앱 번들 없이 실행)에서 성공 응답이 도착하면, 알림 감시는 그 응답을 비교에 쓰지 않고 알던 것(기준점·쿨다운·미뤄 둔 알림)을 버린다. 그 뒤 게이트가 열린 상태에서 받은 첫 응답이 기준점이다 — 보여준 적 없는 알림을 "알렸다" 고 세어 다음 상승을 1시간 눌러 두지 않도록. 초기화는 응답이 도착할 때에만 일어난다: 게이트를 닫았다가 다음 성공 응답이 오기 전에 다시 열면 감시는 닫힌 적이 없는 것처럼 이어진다.
  - 알림 감시는 방금 도착한 응답이 아니라 `OpenClawReading` 이 채택한 마지막 성공의 `host` 를, 그 문서가 신선할 때만 본다 (`ServerHostHealth.reportedHost`). 늦은 도착을 거르는 이유 — 겹친 요청의 늦은 도착이 옛 레벨을 흘려 넣어 현재 레벨을 상승으로 보이게 하지 않도록. 두절 문서를 거르는 이유 — 에이전트가 멈춰도 funnel 은 마지막 파일을 계속 서빙하므로 요청은 성공으로 들어오고, 그 낡은 `host` 가 감시에 계속 들어가면 쿨다운에 눌려 미뤄 둔 알림이 만료 시점에 낡은 값으로 나간다. 그때 팝오버는 "서버 연락 두절" 이라 위의 "두절은 알리지 않는다" 와 어긋난다. 두절은 신호 없음과 같은 취급이라 기준점은 남고, 다시 신선해진 첫 관측에서 여전히 나쁘면 그때 알린다.
  - 신호등 점은 `colorCoding` 토글을 따르지 않는다 — 색이 곧 정보이기 때문이다. 그 토글은 사용량 3단계 색상의 것이다.
  - 세로 스택의 상한은 두 줄이다 — 메뉴바 두께가 22pt 이고, 두 줄과 그 사이 간격(9 + 1 + 9 = 19pt)이 거기 들어가는 한계다. "아래에 쌓는다" 는 수단과 "두 줄까지" 라는 예산은 PHILOSOPHY 가 아니라 이 결정이 소유한다 — 기준 4 가 말하는 것은 폭을 늘리지 않는다는 것뿐이다.
  - 배포 순서 — 서버를 먼저 올려도 구버전 앱은 `host` 를 무시한다. 앱을 먼저 올리면 서버 점이 보이지 않을 뿐이다.
  - #25 의 "판정 외에는 싣지 않는다" 는 "판정과, 표시에 쓰는 상태값(불리언·수치)만 싣는다" 로 넓어진다. 상태값이 모두 판정의 근거인 것은 아니다 — `charging` 은 어느 판정에도 쓰이지 않고 "충전 중" 표시에만 쓰인다. 식별 정보를 싣지 않는 원칙은 그대로이며, `host` 아래 문자열 값이 세 레벨 이름뿐임을 에이전트 테스트가 신호 조합 5가지로 확인한다.
- **트레이드오프**:
  - 세로 스택의 두 줄(위 결과의 상한)을 다 썼다. 폭을 늘리지 않고 들어갈 자리가 더는 없으므로, 세 번째 대상에는 Admission Criteria 4 에 따라 원칙 1 이 그대로 적용된다 — 무언가를 빼야 들어온다.
  - 임계값은 에이전트 소스의 상수다. 바꾸려면 소스를 고쳐 서버에서 다시 설치해야 한다. 설치 플래그로 빼지 않았다.
  - 디스크 여유는 비울 수 있는 공간을 포함한 값을 먼저 쓰므로 `df` 보다 크게 나올 수 있다.
  - 에이전트·앱의 타입 이름(`OpenClaw*`, `mongshell-openclaw-agent`)이 이제 내용보다 좁다. 개명은 설치 스크립트·launchd 레이블을 건드리므로 별도 작업으로 미뤘다.
  - UPS 는 다루지 않는다. 내장 배터리가 없는 서버는 전원 신호가 없다.
  - 배터리로 도는 서버가 잠들면 에이전트도 멈춘다. 그때 앱이 보는 것은 critical 이 아니라 두절이다.
  - 통지 게이트가 닫힌 동안 성공 응답이 한 번이라도 도착했다면, 그동안 나빠진 신호는 게이트를 연 뒤에도 알림으로 오지 않는다 (연 뒤 첫 응답이 기준점) — 점과 팝오버가 보여줄 뿐이다. 그 전에 실제로 보낸 알림의 쿨다운도 함께 잊는다. 닫힌 동안 성공 응답이 없었다면 아무것도 잊지 않는다 — 기준점과 쿨다운이 남아, 그 사이 나빠진 신호는 연 뒤 첫 응답에서 평소 규칙대로 알린다.
  - 위험 수용 — 디스크 여유와 배터리 상태가 정밀값(바이트·퍼센트)으로 공개되므로, 토큰 URL 이 유출되면 값의 변화로 서버의 활동과 전원 상태를 추정할 수 있다. 값을 양자화(구간화)하는 방법은 추정을 조금 어렵게 할 뿐인 데 비해 표시 품질 손해가 커서 하지 않았다. 유출 시 대응은 #25 의 토큰 교체(`--rotate-token`)다.
- **폐기 조건**: 서버가 여러 대가 되거나 사용률 지표가 필요해지면 이 방식으로 늘리지 않는다 — 그것은 범용 모니터의 일이고 범위 밖이다.

## Decision #40: 최소 지원을 macOS 26 으로 — 배포 타깃이 바이너리의 SDK 버전으로 찍히므로

- **도입**: v1.2.0 (#40)
- **컨텍스트**: `swift build` 로 링크한 바이너리의 SDK 버전(`LC_BUILD_VERSION` 의 `sdk`)은 컴파일에 실제로 쓴 SDK(27)가 아니라 `Package.swift` 의 배포 타깃 값으로 찍힌다. SwiftPM 이 `SDKROOT` 없이 컴파일러를 불러 링커가 SDK 버전을 읽지 못하고 배포 타깃으로 채우기 때문이다 (Swift 6.4 툴체인에서 확인 — 같은 링크 명령에 `SDKROOT` 만 주면 27 로 찍힌다). macOS 는 이 값으로 앱에 적용할 호환 동작을 고른다. 배포 타깃이 14 였던 동안 앱은 macOS 27 위에서 "14 SDK 로 만든 앱" 으로 돌았고, 그 동작에서 SwiftUI 는 실행할 때마다 `Settings { EmptyView() }` Scene 을 빈 창("mongshell-menubar Settings")으로 열었다.
- **결정**: 배포 타깃을 macOS 26 으로 올린다 (`Package.swift` 의 `platforms`, `Info.plist` 의 `LSMinimumSystemVersion`).
- **이유**: 이 앱을 쓰는 맥이 모두 macOS 26 이상이라 잃는 것이 없다. 대안은 넷이었다. (a) 15 로만 올림 — 빈 창은 사라지고 화면도 거의 그대로지만, 구형 SDK 호환 동작으로 도는 상태가 남는다. (b) 배포 타깃은 두고 `.app` 조립 때 SDK 버전을 고쳐 찍음(`vtool` 등) — `swift build` 산출물을 그대로 쓰는 스냅샷 렌더와 `.app` 이 서로 다른 동작으로 갈린다. (c) `applicationShouldOpenUntitledFile` 에서 거절 — 시험 앱에서 빈 창을 막지 못했다. (d) SwiftUI App 생명주기를 버리고 Scene 없이 AppKit 으로 — 메인 메뉴(편집 단축키, ⌘,)를 손으로 만들어야 한다.
- **결과**:
  - 앱이 macOS 26 SDK 동작으로 돈다 — 팝오버·설정창의 버튼, 토글, 선택 상자가 macOS 26 디자인으로 그려진다. 메뉴바 아이콘은 그대로다.
  - 배포 타깃을 14 로 되돌리면 빈 창이 돌아온다 (15 에서는 뜨지 않았다).
  - macOS 15 이하에서는 실행되지 않는다. `platforms` 는 패키지 단위라 서버 에이전트도 같다 — 서버 맥도 macOS 26 이상이어야 한다.
  - `PackageDescription` 의 `.v26` 은 tools-version 6.2 부터라, tools-version 6.0 을 유지하려고 문자열 형태 `.macOS("26.0")` 로 적는다.

## Decision #45: GitHub PR 을 단일 status item 안의 옵트인 두 번째 영역으로

- **도입**: v1.2.0 (#45)
- **컨텍스트**: 내 PR 의 리뷰 요청·검사·머지 가능 여부는 브라우저를 열어 확인하러 가는 왕복이 실재한다 ([PHILOSOPHY.md](PHILOSOPHY.md) § Admission Criteria 1). 그러나 #31 이 세로 스택 두 줄을 다 써서, 기준 4(폭을 늘리지 않는다)로는 들어올 자리가 없었다. 두 번째 status item 은 #5 가 배제했고, 신호등 점 하나로 접는 것도 답이 아니었다 — 막힌 PR 의 번호와 개수가 글랜스의 핵심이라 점 하나로는 부족하다. 스택은 Tauri 같은 웹 스택으로 별도 앱을 만드는 안도 검토했으나, 영역 분리 자체가 단일 프로세스를 요구하고 NSPopover 가 공짜로 주는 열기·닫기를 다시 만들어야 해서(#35·#37·#38 의 실패) 배제했다.
- **결정**:
  - (a) [PHILOSOPHY.md](PHILOSOPHY.md) § Admission Criteria 4 에 "옵트인 두 번째 영역" 예외를 신설한다. 같은 status item 안에 세로 헤어라인으로 나뉜 GitHub 영역 — 글리프 `arrow.triangle.pull` · 신호등 점 · 처리할 PR 수 — 을 두고, 기본값은 꺼짐이다. (#52 부터 글리프는 머지 가능한 내 PR 이 있으면 `arrow.triangle.merge` 초록으로 바뀐다.)
  - (b) 영역은 AppKit 자식 호스팅 뷰 2개(`PassthroughHostingView`)로 나눈다. 영역 rect 는 자식 뷰의 프레임이고, hover 트래킹 영역·클릭 판정(마우스 클릭이면 커서의 화면 위치 `NSEvent.mouseLocation` 을 GitHub 영역의 화면 사각형과 대조 — hover 감시와 같은 판정; 키보드·접근성 활성화는 커서와 무관하게 Claude 영역. #58 후속에서 클릭은 사각형 대신 경계 x 로 바뀌었다)·팝오버 앵커(`show(relativeTo: host.frame, of: button)`)가 모두 그 하나를 읽는다. 팝오버는 영역별 NSPopover 2쌍 — 클릭은 `.transient` 로 버튼에, hover 는 `.applicationDefined` 로 보조창에 — 이며 #33/#34/#39 의 구조를 그대로 쓴다. hover 보조창은 하나를 공유하고 영역 프레임에 맞춘다.
  - (c) 인증은 gh CLI 의 Keychain 항목을 Decision 1 과 같은 방식으로 재사용한다 — service `gh:github.com`, account 는 GitHub 사용자명이라 service 만으로 조회한다. 없으면 PAT(classic, `repo`)를 자체 항목(`Config.ownKeychainService` 공유, account `github-pat`)에 둔다. 읽기 순서는 자체 PAT → gh. gh 값의 go-keyring 접두 디코딩은 자격증명 저장소(`GitHubCredentialStore.loadGHToken`)가 끝내고, 모델은 보낼 수 있는 토큰만 받는다. 전송 코드는 openclaw 클라이언트와 `BoundedHTTP` 로 공유한다 — 리다이렉트 거부, 응답 4MB 캡.
  - (d) 갱신은 GraphQL 요청 1회다 — search alias 3개(`review-requested:@me` / `author:@me is:open` / `author:@me is:merged merged:>=7일 전`, 모두 `sort:updated-desc`, 페이지 20)와 `rateLimit { cost remaining limit resetAt }` 를 한 요청에 묶는다. 주기는 백그라운드 3분(설정 1~10분), 팝오버를 열 때 즉시 1회, 열려 있고 진행중 검사(running 또는 queued)가 있으면 30초. 잔량이 200 미만이거나 429/403/`RATE_LIMITED` 를 받으면 사용량 폴링과 같은 지수 백오프이고, 물러나 있는 동안에는 팝오버를 열어도 즉시 요청을 보내지 않는다. 401 을 받으면 자동 폴링을 멈추고 수동 재개(팝오버의 재시도·새로고침, PAT 적용·지우기, gh 토큰 다시 시도, GitHub 표시 다시 켜기)만 남긴다 — 재개한 요청이 다시 401 이면 다시 멈춘다. 401 이나 PAT 저장 실패 상태에서는 팝오버를 열어도 요청하지 않는다. 팝오버의 열림·닫힘은 AppDelegate 가 `NSPopover.didCloseNotification` 으로 모델에 알리되, 닫힘은 요청을 내지도 루프를 재시작하지도 않는다 — 플래그만 바꾸고 다음 깨어남부터 base 주기로 돌아간다. 응답 해석은 `throws(GitHubAPIError)` 다: 401·403/429·2xx 외의 코드(3xx·5xx)와 `data` 없는 본문은 오류이지 빈 목록이 아니다. 그 안에서는 관대하다 — alias 하나가 빠지면 그 목록만 비고, `PullRequest` 가 아닌 노드와 `rateLimit` 누락은 건너뛴다. 1초 경과 타이머는 팝오버 뷰의 `TimelineView` 가 맡고, 스냅샷은 시계를 고정한다.
  - (e) 판정 — 배지 우선순위(충돌 > 검사 실패 > 변경 요청 > 내 리뷰 대기 > Draft > 리뷰 대기 > 승인 > 머지 가능), 머지 가능의 권위는 GitHub 의 `mergeStateStatus`(없으면 승인 + 통과 + `mergeable`), 검사는 같은 워크플로·job 의 최신 실행 하나만 남기고 PR 의 검사 상태는 목록을 끝까지 받았으면 정리된 칩에서·아니면 rollup 에서 읽는 것(규칙은 architecture.md § 4), 메뉴바 숫자(리뷰 요청 + 내 PR 중 막힌 것), 점(빨강/주황/초록, 토큰 없음·오류는 회색), 칩 접기, 시간 포맷 — 은 순수 값 타입에 두고 `scripts/test.sh` 로 고정한다. 모르는 값은 통과로 읽지 않는다: CheckRun 의 모르는 `status` 는 queued, `COMPLETED` 인데 모르는 `conclusion` 은 failed(완료된 검사를 queued 로 두면 열린 팝오버가 30초 주기에 영원히 묶인다), rollup 의 모르는 `state` 는 pending, `mergeable` 의 모르는 값은 unknown(충돌 아님), `mergeStateStatus` 의 모르는 값·누락은 unknown(CLEAN 아님). 모델(`GitHubModel`)은 싱글턴이 아니라 AppDelegate 가 소유하고 주입한다.
- **이유**:
  - 자식 뷰 2개로 나누는 이유 — SwiftUI 좌표를 AppKit 으로 넘기면 영역 rect 의 출처가 비동기 preference 하나가 되고, 그것을 hover·클릭·앵커 셋이 나눠 쓴다. 뷰 프레임은 AppKit 이 동기로 보장한다.
  - gh 토큰을 읽는 이유 — Decision 1 과 같다: 켜자마자 실데이터. gh 는 zalando/go-keyring 으로 저장하므로 Keychain 값에 `go-keyring-base64:` 접두 + base64 가 붙는다 (구버전은 `go-keyring-encoded:` + hex, 더 구버전은 평문). 이 맥에서 실측으로 확인했고, 디코딩은 이 사실에 의존한다.
  - 1요청인 이유 — 한도는 토큰당 시간당 5,000 포인트이고 요청 수가 아니라 노드 수로 과금한다. 묶어도 비용은 같고 왕복과 2차 한도 노출이 준다. 무료 계정도 같은 한도다.
  - 30초인 이유 — 경과 시간이 1초마다 흐르는 동안 상태가 따라와야 한다. 열려 있을 때만이라 비용은 보고 있는 동안만 든다.
  - 401 에서 자동 폴링을 멈추는 이유 — 같은 실패 토큰으로 주기마다 다시 요청하면, 반복된 인증 실패 때문에 GitHub 이 같은 사용자의 유효한 자격증명까지 일시적으로 거부할 수 있다. 그래서 재개는 사용자가 직접 하는 동작에만 묶는다.
  - 싱글턴이 아닌 이유 — Models/CLAUDE.md 의 규칙대로다. AppKit 호스트와 뷰가 같은 인스턴스를 봐야 한다는 싱글턴의 근거는 AppDelegate 가 모든 뷰를 만들어 주입하면 그것으로 성립한다.
  - "승인" 배지를 둔 이유 — 승인됐지만 검사가 도는 PR 에 "리뷰 대기" 를 찍지 않기 위해.
  - 머지 가능을 `mergeStateStatus` 로 판정하는 이유 — 혼자 쓰는 저장소는 리뷰 규칙이 없어 `reviewDecision` 이 null 이다. 승인을 요구하면 그런 PR 은 머지 버튼이 초록이어도 영영 "리뷰 대기" 였다 (실측: mongshell-menubar#46 — reviewDecision null, `MERGEABLE`, `CLEAN`, 검사 없음). `CLEAN` 은 브랜치 보호·필수 검사·필수 리뷰를 GitHub 가 종합한 값이라, 리뷰 규칙이 있는 저장소에서도 같은 뜻이고 앱이 그 규칙을 다시 짐작하지 않는다.
  - 검사를 최신 실행으로 정리하고 끝까지 받은 칩으로 판정하는 이유 — 재실행은 옛 실행을 지우지 않고 같은 이름의 실행을 하나 더 얹는다. `statusCheckRollup.state` 는 그 옛 취소 실행까지 세어 FAILURE 가 되므로, rollup 을 믿으면 최신 실행이 전부 성공인 PR 이 "검사 실패" 로 막히고 칩은 이름이 겹쳐 두 번씩 나온다 (실측: gambau#1982 — static ×2, test CANCELLED→SUCCESS, automerge CANCELLED→SUCCESS, rollup FAILURE). 같은 job 이름이 다른 워크플로에 있을 수 있어(CI 의 `build` 와 Release 의 `build`) 정리 키에 워크플로를 넣는다 — 이름만으로 묶으면 한쪽의 성공이 다른 쪽의 실패를 가린다. 목록을 끝까지 받지 못했을 때(잘림·모르는 노드·`totalCount` 없음·칩 없음)만 rollup 으로 물러난다 — 받지 못한 검사가 실패일 수 있어서다 (규칙은 [architecture.md § 4](architecture.md#4-github-pr-폴링-선택-경로)). #60 후속에서 이름별 정리 앞에 밀려난 실행을 버리는 단계가 붙었다.
- **결과**:
  - 메뉴바 폭이 켠 경우 약 46pt 는다 (#56 부터 약 52pt). 노치 맥북에서 자리가 모자라면 macOS 가 item 전체를 숨긴다 — 끄거나 게이지 표시를 줄이는 것 외에 대책은 없다.
  - 클릭 팝오버가 열린 동안 status item 전체(두 영역)가 강조된다 (#39 와 같은 수용).
  - `mergeable == UNKNOWN` 은 충돌이 아니다 — 다음 폴링에서 확정된다.
  - 섹션당 표시 상한은 리뷰 요청 6 · 내 PR 8 · 최근 머지 3 이고, 넘치면 "외 N건" 행이다. 스크롤은 없다. "외 N건" 의 N 은 받은 페이지(20) 안에서만 센다 — 실측에서 7일 머지가 20에 닿았으므로, 그 너머는 셀 수 없다. search 의 `issueCount` 를 함께 실어 정확한 N 을 내는 것은 후속이다.
  - 토큰 없음·접근 거부·401·한도 초과·HTTP 오류는 배너다. 빈 목록으로 가장하지 않는다. `x-oauth-scopes` 에 `repo` 가 없으면 "비공개 레포가 빠질 수 있음" 배너다.
  - Keychain 접근 거부는 세션 동안 기억하고 설정에서만 재시도한다 — 기억하지 않으면 3분마다 대화상자가 뜬다. 첫 읽기는 설정 토글을 켜는 동작에서 한다.
  - PAT 를 Keychain 에 저장하지 못하면 배너로 알리고, 수동 재개(architecture.md § 4 의 목록 — 팝오버를 여는 것은 포함되지 않는다)까지 자동 요청을 보내지 않는다 — 사용자가 바꿨다고 아는 토큰과 실제로 보내는 토큰이 어긋나지 않게.
  - 팝오버를 열 때의 즉시 갱신은 진행 중인 갱신과 겹쳐도 버려지지 않는다.
  - 라인 diff 는 보여주지 않는다 — 검사별 칩과 소요시간이 그 자리다.
  - 실측 1회(gh 토큰, 2026-10-20): `rateLimit.cost` = 1, remaining 4725/5000, scopes 에 `repo` 있음. CheckRun 에 `checkSuite { workflowRun { workflow { name } } app { slug } }` 를 더한 뒤에도 1이다 — 더한 것은 연결(connection)이 아닌 단일 객체라 비용 계산에 들어가는 연결 수가 그대로다. 1분 주기라도 시간당 60 포인트 안팎이다 — 비용은 노드 수를 따르므로 PR·검사가 많으면 오르지만, 한도(5,000)와는 자릿수가 다르다.
  - 실기 확인 — 검증된 것: 메뉴바에 영역이 생기고, 꺼진 상태의 폭과 스냅샷은 전과 같다. 영역별 hover 요약이 맞게 뜬다(사용자 확인). 클릭을 이벤트 위치(`NSApp.currentEvent` → 버튼 좌표)로 영역에 나누던 첫 구현은 실기에서 GitHub 영역 클릭에 Claude 팝오버를 열었다 — 세 조건(현재 이벤트 존재 · 이벤트 창 = 버튼 창 · 버튼 좌표 포함 판정) 중 어느 것이 틀렸는지는 실측하지 않았고, hover 감시가 쓰는 화면 좌표 판정으로 바꿨다. 미확정: 바꾼 뒤의 클릭 팝오버, Claude 팝오버가 열린 채 GitHub 영역을 클릭했을 때의 전환 여부, 팝오버를 닫은 뒤 30초 → base 주기 복귀. 메뉴바 전용 앱이라 자동 UI 검증 경로가 없어(computer-use 승인 대상이 아니고 합성 입력은 접근성 권한을 요구) 실사용에서 확인한 뒤 여기에 기록한다.
- **트레이드오프**:
  - gh 다중 계정 미지원 — 같은 service 의 항목 중 임의의 하나를 읽고, 배너에 계정명만 표시한다.
  - 팀 단위 리뷰 요청(`team-review-requested`)은 포함하지 않는다.
  - 옛 Commit Status 는 소요시간이 없다.
  - Keychain "항상 허용" 이 ad-hoc 재빌드마다 초기화된다 (Decision 3).
  - 주기를 1분으로 두면 시간당 요청 60회다 — 실측 비용은 요청당 1 포인트지만 노드 수를 따르므로, 받는 PR·검사가 늘면 같이 오른다. 잔량 200 미만에서 백오프가 먼저 걸린다.
  - 머지 20건을 넘는 주에는 "외 N건" 이 실제보다 적다 (위 결과).
- **폐기 조건**: GitHub 가 GraphQL search 비용을 크게 올리거나 PAT 의 search 접근을 막으면 REST 로 재작성하지 않고 기능을 끈다 — 옵트인이라 사라져도 주인공에 영향이 없다.
- **구현 라운드**: 완료 — R0 docs → R1 AppDelegate 영역 파라미터화(동작 보존) → R2 서비스·모델·테스트 → R3 뷰·연결·스냅샷 → R4 문서 마감. "도입" 은 릴리스 시 버전으로 채운다.
- **후속 (#51)**: "리뷰 요청" 을 걷어낸다 — 쿼리의 `review-requested:@me` alias, 팝오버의 리뷰 요청 섹션, "내 리뷰 대기" 배지, 메뉴바 숫자와 주황 점에서 리뷰 요청을 세던 것, hover 의 리뷰 요청 줄. 혼자 개발하는 사용자에게 남이 나를 리뷰어로 지정한 PR 은 늘 0 이라, 그 줄은 hover 의 첫 자리를 차지하면서 아무것도 알려 주지 않았다. 메뉴바 숫자는 이제 내 PR 중 막힌 것만 센다. 위 (d)·(e)·이유·결과의 리뷰 요청·30초 서술과 #49 (b) 의 "리뷰 요청 섹션" 은 이 후속으로 대체된다 (사양은 [architecture.md § 4](architecture.md#4-github-pr-폴링-선택-경로)). 팀 단위 리뷰 요청을 넣지 않는다는 트레이드오프도 함께 의미를 잃는다 — 리뷰 요청 자체가 범위 밖이다. 비운 hover 첫 줄에는 내 PR 의 CI 를 둔다 — PR 을 올린 뒤 실제로 확인하러 가는 것은 검사가 어디까지 왔는지이고, 가장 오래 돈 진행중 검사 하나와 그 경과 시간이면 브라우저를 열지 않아도 된다. 판정은 배지와 같은 `effectiveChecks` 를 읽어 이미 실패한 PR 을 "진행중" 으로 세지 않는다. 메뉴바 점의 주황은 "리뷰 요청만 있음" 에서 "막힘 없이 CI 진행중" 으로 뜻을 바꾼다 — 초록/빨강만 남기는 안도 있었으나, 막힘이 없어도 아직 끝나지 않은 PR 은 "할 일 없음(초록)" 이 아니고, 그 구분이 메뉴바에서 바로 보이면 hover 를 열 이유도 알 수 있다. 숫자는 그대로 막힘만 센다 — 진행중은 기다리면 되는 것이지 처리할 것이 아니다. 같은 까닭으로 30초 주기를 팝오버에서 떼어 낸다 — 내 PR 에 막 시작한 실행중 검사가 있으면 팝오버를 열지 않아도 30초다 (조건은 아래에서 좁힌다). CI 를 hover 로 보게 되면 팝오버가 닫혀 있는 시간이 곧 보는 시간이라, 열려 있을 때만 빠르면 hover 의 상태가 최대 base 주기(기본 3분)만큼 늦는다. 비용은 요청당 1 포인트라 그런 검사가 도는 동안 시간당 약 120 포인트(한도 5,000 의 2~3%)이고, 검사가 끝나거나 60분을 넘기면 base 로 돌아간다. (d) 의 "열려 있고 진행중이면 30초" 와 "닫힘은 다음 깨어남부터 base 로" 는 이것으로 대체된다. 백오프 중 30초 금지와 401·PAT 저장 실패 정지는 그대로 우선한다. 숨긴 레포의 검사는 어디에도 보이지 않으므로 주기를 당기지 않는다. 30초의 조건은 표시의 진행중 판정에서 떼어 좁힌다 — 상태가 정상(`loaded`)이고, 내 PR 중 `effectiveChecks` 가 진행중인 것에 시작한 지 60분 이내인 running 검사가 있을 때만 30초, 그 외 base 다. 표시와 같은 판정을 쓰던 첫 구현에는 30초가 끝나지 않는 경로가 둘 있었다. 하나는 토큰 없음·Keychain 거부·오류처럼 점이 회색인 상태에서도 지난 스냅샷이 진행중이면 30초가 남은 것이다 — 지난 답은 지금 상태를 말하지 않고, 빠른 요청은 같은 실패를 되풀이할 뿐이다. 다른 하나는 끝나지 않을 수 있는 대기가 무기한 붙잡은 것이다 — 외부 상태가 보고하지 않은 StatusContext(PENDING/EXPECTED), 승인 대기나 꺼진 러너에 걸린 queued CheckRun, 칩 없이 rollup 만 진행중인 PR. 그래서 표시는 사실대로 두고(주황 점·hover CI 줄은 이것들을 여전히 진행중으로 보인다) 비용만 묶는다 — 시작 시각을 아는 막 시작한 실행만이 곧 끝나 상태가 바뀐다고 말해 주고, 60분 넘게 도는 실행은 base 주기로 따라잡아도 늦지 않다. 시작 시각이 없는 running 은 얼마나 돌았는지 모르므로 근거로 쓰지 않는다. 결과의 미확정 항목 "팝오버를 닫은 뒤 30초 → base 주기 복귀" 는 주기가 팝오버 열림과 무관해져 확인할 대상이 사라졌다. 한도 헤더 없는 403·429 도 지수 백오프에 넣는다 — GitHub 은 보조 한도를 헤더 없이 알리기도 하고 그때는 최소 1분 기다린 뒤 지수 백오프로 재시도하라고 안내하는데, 오류로만 다루면 base 주기로 같은 요청이 되풀이되고 팝오버를 열 때마다 즉시 한 번 더 나갔다. 상태를 한도로 바꾸지 않는 것은 헤더 없이는 한도였다고 단정할 수 없어서다 — 403 은 권한 거부이기도 하다.
- **후속 (#58)**: 클릭 판정을 영역 사각형 포함에서 경계 x 하나로 바꾼다. 실측 메뉴바는 30pt(노치 맥은 더 높음)인데 버튼은 `NSStatusBar.thickness`(22pt)이고, 메뉴바 전체 높이와 아이템 옆 여백의 클릭이 모두 버튼에 온다. 사각형 포함으로 판정하면 그 클릭이 전부 "GitHub 영역 밖" 이 되어 Claude 팝오버가 열렸다 — GitHub 영역 가장자리를 누르면 Claude 가 뜨는 버그. 이제 마우스 클릭은 커서 x 가 GitHub 영역의 화면상 왼쪽 끝(헤어라인 칸 포함) 이상이면 GitHub, 아니면 Claude 이고, 영역 폭이 0(꺼짐)이거나 프레임이 없으면 Claude 다 (`RegionClickRouting`, `scripts/test.sh` 로 고정). hover 는 사각형 판정 그대로다 — hover 요약을 닫는 watchdog 은 커서가 영역을 떠났는지를 물어야 하고, 위아래로 벗어난 커서는 떠난 것이 맞다.
- **후속 (#60) — 밀려난 실행**: 검사 정리 앞에 "밀려난 실행 버리기" 를 붙인다 — CheckRun 의 `checkSuite.workflowRun { runNumber event workflow { databaseId } }` 를 함께 받아, (워크플로 id, `event`)별로 가장 큰 `runNumber` 보다 작은 실행의 CheckRun 을 버린 뒤 기존 (워크플로, job 이름)별 최신 정리를 그대로 적용한다 (같은 실행 안의 재시도는 `runNumber` 가 같아 이 뒷단계가 맡는다). 이름별 정리만으로는 새 실행에 아직 없는 job 의 이전 실행 기록이 살아남는다 (실측: gambau#2014 — PR 생성으로 시작한 `verify` 874 가 `automerge` 라벨의 `labeled` 이벤트로 시작한 875 에 `concurrency: cancel-in-progress` 로 취소돼 test·static·automerge 가 CANCELLED 였고, 875 에는 `automerge` 잡이 `needs: [static, test]` 때문에 test 가 끝날 때까지 아예 없었다. 874 의 CANCELLED automerge 하나가 남아 약 6분간 "검사 실패" 였다). GitHub 화면은 같은 워크플로의 새 실행이 생기면 이전 실행의 검사를 통째로 숨기므로, 앱도 job 이름이 아니라 실행 단위로 버린다. 키에 `event` 를 넣는 이유 — 같은 워크플로가 `push` 와 `pull_request` 로 따로 돌면 두 실행은 서로를 대체하지 않는다 (`labeled` 같은 활동 유형은 `event` 가 모두 `pull_request` 라 같은 계열이다). 워크플로를 표시 이름(YAML `name:`)이 아니라 id(`databaseId`)로 묶는 이유 — 이름이 같은 서로 다른 워크플로 파일이 있을 수 있고 `runNumber` 는 파일마다 따로 세므로, 이름으로 묶으면 번호가 큰 쪽이 다른 파일의 실행을 통째로 버려 실제 실패를 숨긴다 (재실행 정리 키 `RerunKey` 는 이름 그대로다). 워크플로 id·`event`·`runNumber` 중 하나라도 읽지 못한 CheckRun, `workflowRun` 이 없는 다른 앱(Vercel 등)의 검사, StatusContext 는 버리지 않는다 — 정보가 없으면 밀려났다고 단정하지 않는다. 버린 CheckRun 도 "읽은 것" 이라 끝까지 받았는지(`totalCount` == 읽은 수)의 판정은 그대로다. 쿼리 비용: 더한 세 필드(`runNumber`·`event`·`workflow.databaseId`)는 단일 객체의 스칼라라 연결 수가 그대로이고, 실측(gh 토큰, 2026-10-21, `databaseId` 포함 쿼리)에서도 `rateLimit.cost` = 1 이다 (사양은 [architecture.md § 4](architecture.md#4-github-pr-폴링-선택-경로)).

## Decision #47: 앱 번들 버전은 빌드 시 git tag 에서 찍는다

- **도입**: v1.2.0 (#47)
- **컨텍스트**: 버전 SSOT 는 git tag 다 (`docs/architecture.md` § 배포, `/release` 는 태그만 만들고 파일을 고치지 않는다). 그런데 `Resources/Info.plist` 의 `CFBundleShortVersionString` 은 손으로 적은 `0.1.0` 이었고 `make_app.sh` 가 그대로 복사해, 태그가 `v1.1.2` 인데도 앱은 0.1.0 으로 찍혔다. 사용자에게 보이지 않아 드러나지 않았지만, GitHub PR 영역(#45)이 GitHub API 요청의 `User-Agent` 에 이 값을 싣도록 설계돼 외부로 나가는 값이 된다.
- **결정**: `make_app.sh` 가 번들을 조립할 때 `git describe --tags --abbrev=0 --match 'v[0-9]*'` 로 가장 가까운 태그를 읽어, `vX.Y.Z` 형식이면 번들 안 `Info.plist` 사본의 `CFBundleShortVersionString` 을 그 값으로 바꾼다 (서명 전에). 저장소의 `Info.plist` 에는 `0.0.0` 자리표시만 둔다. `release.sh` 는 `make_app.sh` 를 거치므로 같은 값을 받는다.
- **이유**: 대안은 셋이었다. (a) 릴리스마다 `Info.plist` 를 손으로 올림 — 태그와 파일 두 곳에 같은 값을 복제하는 것이고, `/release` 가 파일을 고치지 않는 불변식 때문에 별도 chore PR 이 매번 필요해 결국 밀린다 (지금 상태가 그 결과다). (b) `git describe` 전체 문자열(`1.1.2-5-gabc1234`)을 씀 — `CFBundleShortVersionString` 은 마침표로 나뉜 정수 세 개여야 해서 넣을 수 없다. (c) 빌드 시 가장 가까운 태그 — 파생 가능한 값을 복제하지 않고, 형식도 지킨다.
- **결과**:
  - 태그 사이의 개발 빌드는 직전 릴리스 번호로 찍힌다 (`v1.1.2` 뒤 커밋도 1.1.2). 어느 커밋인지는 번들 버전으로 구분하지 않는다.
  - 태그를 볼 수 없는 빌드(`.git` 없는 소스 사본, 태그를 fetch 하지 않은 clone)는 `0.0.0` 으로 남고 `make_app.sh` 가 그 사실을 출력한다. 태그가 `vX.Y.Z` 형식이 아니어도(예: `v1.2.0-rc1`) 같다. 로컬 빌드는 그대로 진행하지만, 남에게 주는 `release.sh` 는 `0.0.0` 이면 서명·공증 전에 멈춘다.
  - `CFBundleVersion` 은 `1` 그대로 둔다 — 자동 업데이트 수단이 없어 빌드 번호를 비교하는 쪽이 없다.
  - 되돌리려면 `make_app.sh` 의 버전 블록과 `release.sh` 의 `0.0.0` 검사를 지우고 `Info.plist` 에 실제 버전을 적으면 된다.

## Decision #49: 내 PR 의 squash 머지를 팝오버에서 — 첫 원격 쓰기

- **도입**: v1.2.0 (#49)
- **컨텍스트**: #45 로 내 PR 의 막힘·검사 상태를 메뉴바에서 보게 됐지만, "머지 가능" 배지가 붙은 PR 을 머지하려면 브라우저로 다시 가야 했다. 막힘이 없다는 것을 이미 앱이 보여 준 뒤라, 남은 왕복은 버튼 한 번을 누르러 가는 것뿐이다. 그런데 [PHILOSOPHY.md](PHILOSOPHY.md) § Out of Scope 는 "승인·머지 같은 쓰기 동작" 을 범위 밖에 두었고, 이 앱에는 지금까지 원격에 쓰는 동작이 하나도 없었다.
- **결정**:
  - (a) Out of Scope 를 "내 PR 의 squash 머지 하나 외의 쓰기 동작" 으로 좁힌다. 승인·코멘트·라벨·다른 머지 방식(merge commit·rebase)·브랜치 삭제는 여전히 범위 밖이다.
  - (b) 버튼은 "내 PR" 섹션의 행에서, GitHub 의 `mergeStateStatus == CLEAN` 이고 Draft 가 아니며 그 PR 의 노드 id 와 head 커밋 SHA 를 받았고 PR 링크가 https·github.com 검사를 통과했을 때만 그린다 — 링크가 걸러진 응답에는 되돌릴 수 없는 쓰기를 권하지 않는다. 조건이 맞지 않으면 회색으로 두지 않고 그리지 않는다 (원칙 2). 리뷰 요청 섹션(남의 PR)과 최근 머지 섹션에는 없다.
  - (c) 한 번 클릭으로 바로 요청을 보낸다 (처음엔 두 번 눌러야 실행했다 — 아래 후속). NSPopover 안이라 시스템 경고창은 쓰지 않는다. 보내는 커밋은 클릭 순간 그 행에 보이는 head 다.
  - (d) 요청은 GraphQL `mergePullRequest` 하나이고, `mergeMethod: SQUASH` 와 클릭 순간 그 행에 보인 head SHA 를 `expectedHeadOid` 로 넘긴다. 앱은 브랜치 삭제 인자를 보내지 않는다 — 원격 브랜치를 지울지는 저장소의 자동 삭제 설정을 따른다. squash 커밋의 제목·본문은 GitHub 기본값에 맡긴다.
  - (e) 보내기 전에 모델이 그 PR 을 뷰가 넘긴 사본이 아니라 현재 스냅샷에서 다시 꺼내 판정하고, 401 같은 정지 상태에선 보내지 않는다. 토큰을 바꾼 뒤 새 토큰의 목록이 오기 전에도 보내지 않는다 — 화면의 목록은 이전 토큰이 본 것이다. 성공하면 즉시 갱신하되, 백오프 중이면 다음 정기 갱신에, 요청이 나가 있는 동안 401·PAT 저장 실패로 멈췄으면 사용자의 수동 재개까지 미룬다 (멈춘 상태에서는 머지를 보내지 않는다). 실패하면 GitHub 이 준 사유를 그 행 아래 한 줄로 보이고, 다음 성공한 갱신까지 둔다. 401 은 #45 (d) 의 정지 규칙을 그대로 탄다.
- **이유**:
  - `CLEAN` 만 보는 이유 — 혼자 쓰는 저장소는 리뷰 규칙이 없어 `reviewDecision` 이 null 이므로, 승인 여부는 신호가 되지 못한다. `CLEAN` 은 브랜치 보호·필수 검사·필수 리뷰를 GitHub 가 종합한 판정이라, 그것이 GitHub 의 머지 버튼이 초록인 조건과 같다 (#45 (e) 의 "머지 가능" 과 같은 근거). 앱이 그 규칙을 따로 짐작하지 않는다.
  - `expectedHeadOid` 를 넘기는 이유 — 없으면 사용자가 본 것과 다른 커밋이 머지될 수 있다. 화면은 폴링 주기만큼 늦고, 그 사이 올라온 커밋은 검사도 보지 않은 채 함께 머지된다. 이 값이 있으면 GitHub 가 head 가 바뀐 머지를 거절한다.
  - 경고창을 쓰지 않는 이유 — 경고창은 팝오버를 닫거나 포커스를 빼앗는다. 확인 단계를 두지 않는 이유는 아래 후속.
  - 스냅샷에서 다시 판정하는 이유 — 되돌릴 수 없는 요청이라, 뷰가 그릴 때의 사본보다 모델이 아는 현재를 믿는다. 정지 상태에서 머지만 나가면 #45 (d) 가 막으려던 거부된 토큰의 재전송이 된다. 같은 까닭으로 성공 직후의 갱신도 백오프를 건너뛰지 않는다.
  - squash 하나인 이유 — 이 프로젝트의 머지 규약이 squash 다. 방식을 고르는 UI 는 메뉴바 앱의 일이 아니고, 다른 방식이 필요하면 웹에서 한다.
  - 그리지 않는 이유(회색이 아닌) — 원칙 2. 조건 밖의 PR 에는 이미 배지가 그 사유를 말한다.
- **결과**:
  - 이 앱의 첫 원격 쓰기다. 토큰이 하는 일이 읽기에서 머지까지 넓어진다 — classic PAT 의 `repo`, gh 토큰의 `repo` scope 로 충분하고, 권한이 모자라면 행 아래 실패 사유로 보인다.
  - 앱은 브랜치를 지우지 않는다. 이 저장소는 그 설정(`deleteBranchOnMerge`)이 꺼져 있어(2026-10-20) 원격 브랜치가 남았다. 조직 `mongshell-io` 로 이관한 뒤(2026-10-24)에는 켜져 있어 머지된 원격 브랜치를 GitHub 이 지운다.
  - 머지 직후의 갱신에서 search 색인이 늦으면 PR 이 잠시 "내 PR" 에 남을 수 있다 — 그 동안 그 행은 버튼 대신 "머지됨" 을 보이고, 목록에서 빠지면 그 표시도 사라진다.
  - head 가 바뀌어 거절된 경우에도 버튼은 남는다 — 다음 갱신이 새 head 를 받아 와야 다시 머지할 수 있다. 클릭 직전에 갱신이 새 head 를 받아 와 행이 본 head 와 어긋나면 GitHub 에 묻지 않고 행에 사유가 남는다.
- **트레이드오프**:
  - 머지 큐·자동 머지는 다루지 않는다. 머지 큐가 필요한 저장소에서는 GitHub 가 거절하고, 그 사유가 행에 보인다.
  - squash 커밋 메시지를 고칠 수 없다 — 저장소의 squash 커밋 기본값(제목·본문 설정)이 그대로 들어간다.
  - 머지가 성공했는데 응답이 유실되면(타임아웃) 실패로 보인다. 다음 갱신이 실제 상태를 보여 준다.
- **폐기 조건**: GitHub 가 `mergePullRequest` 의 `expectedHeadOid` 를 없애거나 무시하면 버튼을 뺀다 — 본 것과 다른 커밋이 머지될 수 있는 버튼은 두지 않는다.
- **후속 (#49)**: 실사용(PR #50 을 앱 버튼으로 머지)에서 두 번 누르는 확인이 번거로워 한 번 클릭으로 바꿨다. 잘못 누르면 바로 머지되는 위험을 받아들인다.
  - 두 번 누르기를 택했던 근거를 알고도 받아들였다 — 행 전체가 브라우저를 여는 링크라 오클릭이 잦은 자리라는 것, 확인을 head 에 묶은 것은 확인이 "이 커밋을 머지한다" 는 결정이라 다른 커밋이나 다음 열림으로 살아남으면 안 됐기 때문이라는 것, 더블클릭을 확인으로 치지 않은 것은 더블클릭이 두 번의 결정이 아니라 한 동작이기 때문이라는 것.
  - 받아들일 수 있는 이유 — 버튼이 보이는 PR 은 GitHub 가 `CLEAN` 으로 판정한 내 PR 이라, 잘못 눌러도 결과는 어차피 머지할 것을 조금 일찍 머지한 것이다. 보내는 커밋은 클릭 순간 그 행에 보인 head 뿐이다 (`expectedHeadOid`).
  - 버튼 라벨에 PR 번호를 넣는다 ("#N 머지") — 갱신으로 레이아웃이 움직인 순간의 클릭이 어느 PR 에 간 것인지 버튼이 말한다.
  - "머지 중…" · "머지됨" 라벨도 버튼과 같은 자리·같은 폭에서 클릭을 흡수한다 — 더블클릭의 두 번째 클릭이 행의 링크로 떨어져 브라우저를 열지 않는다.
  - 목록을 받은 토큰 출처(PAT · gh 계정)와 머지에 쓸 토큰의 출처가 다르면 보내지 않는다 — 앱 밖의 `gh auth switch` 는 세대를 바꾸지 않아, 이전 계정이 본 목록으로 다른 계정의 머지가 나갈 수 있었다.

## Decision #52: 머지 가능한 내 PR 을 메뉴바 글리프로

- **도입**: v1.2.0 (#52)
- **컨텍스트**: #49 로 팝오버에서 머지할 수 있게 됐지만, GitHub 영역은 막힌 PR 이 없고 CI 가 돌지 않으면 초록 점만 보인다. 머지할 PR 이 있는지는 팝오버를 열어 머지 버튼을 찾아봐야 알아서, 그것을 확인하려고 계속 클릭하게 됐다. 그런데 영역은 #45 (a) 에서 "글리프 · 점 · 숫자 하나" 를 상한으로 받았고 숫자 칸은 이미 처리할 PR 수가 쓰고 있다.
- **결정**:
  - (a) "지금 머지 가능" 은 팝오버의 머지 버튼과 같은 기준이다 — 팝오버에 그려지는 내 PR 행(숨긴 레포 제외, 섹션 상한 `Config.githubSectionCaps.mine` 까지 — 그 너머는 "외 N건" 으로 접혀 버튼이 없다) 중 `GitHubMergePolicy.canOffer(_, section: .mine)` 이 참인 것. 그 PR 의 머지 요청이 나가 있거나(`.merging`) 끝난(`.merged`) 것은 세지 않는다. 실패(`.failed`)는 버튼이 다시 나오므로 센다. 판정은 `GitHubGlance` 의 순수 함수가 모델의 머지 상태를 인자로 받아 하고, 모델은 머지 상태가 바뀔 때마다 glance 를 다시 계산한다.
  - (b) 메뉴바는 폭을 늘리지 않고 글리프로 말한다 — 하나 이상이면 `arrow.triangle.merge` 초록(`Palette.green`), 없으면 지금의 `arrow.triangle.pull` 회색. 두 글리프는 pull 글리프 폭의 고정 칸에 그린다 (#56 후속에서 대체 — 알약 폭 14pt 고정 칸). 색은 신호등 점처럼 `colorCoding` 대상이 아니다.
  - (c) 개수와 어느 PR 인지는 hover 셋째 줄 "머지 가능 N · <레포 이름> #<번호> 외 K" 다. 0 이면 "머지 가능 0" 으로 없음을 말하고, 숫자는 1 이상일 때 초록이다. 메뉴바 숫자·점에는 더하지 않는다.
- **이유**:
  - 숫자를 하나 더 두지 않고 글리프를 바꾼 이유 — 영역 상한(글리프 · 점 · 숫자 하나)과 폭 불변을 지키는 유일한 자리가 글리프다. 묻는 것이 "머지할 게 있는가 / 없는가" 라 이진 신호로 충분하고, 개수는 흘긋 볼 때 필요하지 않아 hover 로 미룬다. 기존 숫자에 더하면 "처리할 것(막힘)" 과 "할 수 있는 것(머지)" 이 한 숫자에 섞여 빨강·주황 점과도 어긋난다.
  - 팝오버 버튼과 같은 기준인 이유 — 메뉴바가 "있음" 이라 했는데 팝오버에 버튼이 없으면 신호를 믿지 못하게 된다. 판정 함수와 섹션 상한을 같은 원천에서 읽으면 두 곳이 갈라질 수 없다.
  - `.merging` · `.merged` 를 빼는 이유 — 머지 직후 search 색인이 늦어 PR 이 잠시 "내 PR" 에 `CLEAN` 으로 남는다. 그 동안 글리프가 초록이면 방금 머지한 것을 "아직 할 일" 로 거짓 표시한다. 팝오버에서도 그 행은 버튼 대신 "머지 중"·"머지됨" 이다.
  - 고정 칸인 이유 — merge 글리프가 pull 보다 약 2/3pt 넓어, 바뀔 때마다 status item 이 흔들린다. 칸을 pull 폭에 맞추면 꺼진 상태·#45 의 폭과 스냅샷이 그대로다. (#56 후속에서 칸을 알약 폭으로 넓혔다 — 폭 불변 취지는 유지)
- **결과**:
  - 메뉴바 폭은 그대로다 — 머지 가능 있음/없음 스트립 스냅샷이 글리프 칸 밖에서 픽셀 단위로 같다. merge 글리프는 칸 양옆으로 1/3pt 씩 넘쳐 간격에 걸친다. (#56 후속에서 영역이 상시 6pt 넓어졌다)
  - hover 가 세 줄이 된다.
  - 머지 가능 PR 이 있어도 점은 초록 그대로다 — 막힘이 없고 CI 가 돌지 않는다는 뜻은 바뀌지 않는다.
- **트레이드오프**:
  - 글리프 모양 차이(pull ↔ merge)는 작다 — 색(회색 ↔ 초록)이 주 신호다 (#56 후속 — 가는 글리프의 색만으로는 실제로 보이지 않아 알약으로 보강). 색을 구분하기 어려우면 모양 차이만 남는다. 접근성 레이블("머지 가능한 PR 있음/없음")로 보완한다.
  - 숨긴 레포의 머지 가능 PR 은 알리지 않는다 — 숨김은 어디에도 세지 않는다는 #45 의 규칙을 따른다.
- **후속 (#56) — 글리프 색만으로는 안 보였다**:
  - 컨텍스트: 10pt medium 글리프의 선이 가늘어, 실제 메뉴바에서 회색 → 초록 변화를 흘긋 봐서는 알아채지 못했다. 위 트레이드오프의 "색이 주 신호" 가 성립하지 않았다.
  - 결정: 머지 가능이면 `Palette.mergePillFill`(= `green`)로 채운 14×13pt 둥근 알약 위에 merge 글리프를 흰색(`mergePillGlyph`) 9pt bold 로 그린다. 없으면 기존 회색 pull 글리프 그대로다. 글리프 칸은 상태와 무관하게 알약 폭(14pt)으로 고정한다 — (b) 의 "pull 글리프 폭 고정 칸" 을 대체한다.
  - 이유: 채운 면적이 선보다 훨씬 커서 색 변화가 글랜스에 들어온다. 알약은 자기 배경이라 상태바 라이트·다크 어디서나 같은 대비다. 칸을 알약 폭으로 고정하면 상태가 바뀌어도 status item 이 흔들리지 않는다는 (b) 의 폭 불변을 지킨다.
  - 결과·트레이드오프: 영역이 상시 6pt 넓어진다(약 46 → 52pt) — 머지 가능 여부가 바뀔 때마다 옆 항목이 밀리는 것보다 낫다고 봤다. 알약은 영역에서 가장 강한 시각 요소가 되지만, 막힘(빨간 점 + 숫자)보다 덜 급한 신호다 — 머지 가능은 "할 수 있는 것" 이라 눈에 띄는 쪽이 맞다고 봤다.

## Decision #68: 로컬 빌드는 팀 ID 가 있는 Apple Development 인증서로 서명한다

- **도입**: 미정 (#68)
- **컨텍스트**: 재빌드한 앱을 처음 띄울 때마다 키체인 접근 프롬프트가 다시 떴고, 거부하면 토큰을 못 읽어 로그인을 다시 요구했다. Decision 3 은 이것을 ad-hoc 서명의 대가로 받아들였고, `make_app.sh` 는 자기 서명 인증서(`mongshell-menubar Dev`)로 서명하면 designated requirement 가 `certificate leaf` 로 고정되어 해결된다고 보았다. 그러나 키체인은 ACL 과 별도로 항목의 **파티션 목록**을 검사하고, 파티션 ID 는 서명에 팀 ID 가 있으면 `teamid:`, 없으면 `cdhash:` 다. 자기 서명 인증서에는 팀 ID 가 없어 빌드마다 새 `cdhash:` 가 되고, ACL 이 맞아도 프롬프트가 다시 떴다. 2026-10-21 에 비밀값 없이 ACL 을 덤프해 보니 `gh:github.com` 항목의 파티션 목록에 `cdhash:` 가 15개 쌓여 있었고, `com.mongshell.menubar.tokens` 는 ACL 앱이 인증서 요구사항 하나뿐인데 파티션에 `cdhash:` 가 3개였다.
- **결정**: `make_app.sh` 는 서명 신원을 이 순서로 고른다 — 명시한 `SIGN_ID` → 키체인의 유효한 `Apple Development:` 신원(이름이 아니라 SHA-1 로 지정) → 자기 서명 `mongshell-menubar Dev` → ad-hoc. 인증서 서명에는 `release.sh` 처럼 hardened runtime(`--options runtime`)을 켠다. README 는 자기 서명 인증서 대신 Apple Development 인증서 발급을 안내하고, 그 개인 키가 `codesign` 에 이미 열려 있어 무엇이 넓어지는지 적는다.
- **이유**: 대안은 셋이었다. (a) 자기 서명 인증서 유지 — 위 증거대로 파티션 검사에서 걸려 문제를 풀지 못한다. (b) Data Protection 키체인 + access group — 엔타이틀먼트와 프로비저닝이 필요하고, 다른 앱의 항목(Claude Code·gh CLI)은 여전히 기존 키체인에 있어 그 프롬프트는 남는다. (c) Apple Development 인증서 — 무료 Apple ID 로 Xcode 에서 발급되고 팀 ID 가 찍혀 파티션 ID 가 `teamid:` 로 빌드와 무관해진다. 발급에만 Xcode 가 필요하고 빌드는 계속 Command Line Tools 로 되므로 Decision 3·#11-1 의 "Xcode 없이 빌드" 전제를 깨지 않는다.
- **결과**:
  - Apple Development 인증서가 있는 맥에서는 서명이 바뀐 직후 항목마다 한 번 *항상 허용* 하면 그 뒤 재빌드에 묻지 않는다.
  - 인증서가 없는 맥은 지금과 같다 — 자기 서명이나 ad-hoc 으로 떨어지고 빌드마다 재승인이 필요하다. 기본 설치 경로는 여전히 Apple 계정이 필요 없다.
  - 자기 서명 경로는 기존 설정을 깨지 않으려고 폴백으로만 남긴다. 프롬프트 측면의 이득은 없다.
  - Decision 3 의 "Developer ID 로 서명하면 토큰이 유지된다 — 유료 경로의 실질 이득" 은 남에게 배포하는 경우(Gatekeeper·공증, 받는 사람의 토큰 유지)로 좁혀진다. 직접 빌드하는 사람은 무료 Apple ID 로 같은 효과를 얻는다.
- **트레이드오프**:
  - 허용 범위가 넓어진다. 전에는 승인이 그 빌드 하나(`cdhash:`)에 묶였지만, 이제는 identifier 가 `com.mongshell.menubar` 이고 이 Apple ID 의 Apple Development 인증서로 서명된 모든 바이너리가 앱이 만든 항목(`com.mongshell.menubar.tokens` 의 OAuth 토큰, 자체 GitHub PAT 항목)을 프롬프트 없이 읽는다. ACL 이 인증서 이름까지 보므로 팀 ID 만 같은 다른 인증서로는 안 된다.
  - 그 경계는 두 가지에 기댄다. 하나는 서명 개인 키다 — Xcode 가 만든 개인 키는 ACL 에 `/usr/bin/codesign` 이 들어 있어 (2026-10-21 이 맥에서 비밀값 없이 확인) 같은 사용자의 아무 프로세스나 묻지 않고 이 신원으로 서명할 수 있다. 넓어진 범위는 기본으로 열려 있고, README 가 이 사실을 적는다. 다른 하나는 프로세스 무결성이다 — hardened runtime 으로 이미 서명된 앱에 라이브러리를 주입하는 경로를 막는다.
  - 수용 근거: 1인용 도구다. 그리고 `Claude Code-credentials` 와 `gh:github.com` 은 ACL 에 `/usr/bin/security` 가, 파티션 목록에 `apple-tool:` 이 들어 있어 같은 사용자 프로세스가 `security` 명령으로 원래부터 프롬프트 없이 읽을 수 있다 (2026-10-21 비밀값 없는 ACL 덤프). 같은 사용자로 도는 악성 코드에 대해 새로 열리는 것은 앱이 만든 항목뿐이다.
  - 개인 팀의 Apple Development 인증서는 유효기간이 있어 재발급이 필요하다. 이 서명의 designated requirement 는 인증서 지문이 아니라 Apple 앵커와 인증서 이름(`certificate leaf[subject.CN]`)으로 정해지므로, 재발급한 인증서의 이름이 같으면 ACL 이 그대로 맞고 팀 ID 가 같아 파티션 목록도 유지된다. 이름이 바뀌거나 다른 Apple ID 로 바꾸면 항목마다 한 번 다시 허용해야 한다.

## Decision #75: 상태 문서에 서버 CI 러너 신호를 추가

- **도입**: 미정 (#75)
- **컨텍스트**: gambau·sellcaddie·k2sell 의 CI 는 서버 맥의 조직 공용 self-hosted 러너 4개(LaunchDaemon `com.github.actions-runner.org`, `…org-2`, `-3`, `-4`)에서 돈다. 러너가 죽어도 조용하다 — 프로세스가 죽으면 `KeepAlive` 가 다시 띄우지만, 그렇지 못한 상태면 잡이 대기열에 쌓였다가 24시간 뒤에야 실패하고, 지금은 "PR CI 가 시작을 안 한다" 로만 알아챈다. 14일 넘게 연결되지 않은 러너는 GitHub 이 등록을 지워, 맥을 다시 켜도 설치 스크립트를 다시 돌려야 한다.
- **결정**: #31 의 `host` 에 `runners` 신호를 더한다. 에이전트가 `/Library/LaunchDaemons/com.github.actions-runner.*.plist` 개수를 `total` 로, 그 레이블 중 `launchctl print system/<레이블>` 의 최상위 `state = running` 인 수를 `running` 으로 세고, `host.runners = { health, running, total }` 을 싣는다. 판정은 #31 과 같이 `HostRules` 한 곳에 있고 종합 `host.health` 에 합쳐진다. 앱은 관대하게 읽어 서버 점의 종합 판정·팝오버 서버 섹션의 `CI 러너 3/4` 줄·신호별 알림에 반영한다. `schema` 는 1 그대로다 (키 추가 — #31 과 같은 이유).
- **판정 규칙** (에이전트 `HostRules`):
  - `running == total` → ok, `0 < running < total` → warning, `running == 0` → critical.
  - plist 가 하나도 없으면 신호 자체가 없다 (`runners: null`). 러너 대수는 하드코딩하지 않는다 — 설치된 만큼이 `total` 이다.
  - `launchctl print` 의 응답이 최상위(탭 1개) `state = running` 이 아니면 그 러너는 동작으로 세지 않는다. 하위 블록(endpoints 등)의 `state = active` 같은 줄은 보지 않는다. 서비스가 로드되지 않았다는 응답("Could not find service", exit≠0)도 응답이므로 "동작 안 함" 이다.
  - 어느 한 레이블이라도 launchctl 을 **듣지 못하면**(실행 실패·시간 초과·신호 종료·빈 출력) 신호 전체가 `null` 이다. 들은 응답을 해석하지 못한 것(동작 안 함)과 듣지 못한 것(모름)을 가른다.
- **이유**:
  - **A안(에이전트 로컬 launchctl) vs B안(GitHub API).** B안은 메뉴바 앱이 `orgs/mongshell-io/actions/runners` 를 읽는 것이다. GitHub 이 보는 online/offline·busy 가 진실값이라는 장점이 있지만, classic 토큰이면 `admin:org`(쓰기 포함) 스코프가 필요해 메뉴바의 GitHub 자격증명(Decision #45 — gh 의 Keychain 항목 재사용) 권한을 크게 넓혀야 한다. fine-grained 토큰의 조직 "Self-hosted runners: read" 로 되는지는 확인되지 않았고, 된다 해도 새 토큰 관리가 생긴다. A안은 이미 서버 맥에서 도는 에이전트가 sudo 없이 `launchctl print` 로 읽고 기존 경로(에이전트 → 상태 파일 → 앱의 관대한 읽기)에 신호 하나를 더할 뿐이라 새 권한·새 네트워크 경로·새 자격증명이 없다. 1인 운영의 단순성과 권한 최소화를 위해 A 를 골랐다.
  - 꺼짐·잠자기는 A안의 약점이 아니다 — 서버 맥이 꺼지거나 잠들면 에이전트도 멈추고, 상태 문서의 신선도(두절) 규칙(#25)이 이미 서버 점을 회색으로 만든다.
  - launchctl 을 듣지 못하면 신호 전체를 버리는 이유 — #31 의 "재지 않은 판정을 싣지 않는다". 동작 안 함으로 세면 spawn 실패 한 번이 "러너 전부 중단" 이라는 거짓 critical 이 되고, 동작으로 세면 아무도 재지 않은 ok 가 된다. 신호가 빠지면 앱은 러너 줄을 그리지 않고, 에이전트가 종합 레벨을 남은 신호로 계산하므로 서버 점에서도 러너가 빠진다. 알림 감시만 마지막 러너 레벨을 기준으로 남긴다 (#31 의 "신호가 사라진 것은 알리지 않는다") — 거짓 경보도 회복 알림도 없다.
  - 러너 단계 전체에 마감(10초)을 두는 이유 — 레이블마다 순차로 묻기 때문에, launchd 가 레이블마다 멈추면 레이블당 타임아웃이 대수만큼 쌓여 확인 주기를 잡아먹는다. 정상이면 4대를 묻는 데 1초도 걸리지 않는다. 마감을 넘기면 남은 레이블은 묻지 않고 "듣지 못함" 규칙대로 신호 전체를 버린다. 마감이 가까우면 레이블당 타임아웃도 남은 시간으로 줄인다.
  - 상태 한 마디·알림 문구의 "일부 중단"/"전부 중단" 을 레벨이 아니라 개수로 고르는 이유 — #31 의 전원 원인 문구와 같다. 레벨은 앱이 판정을 읽지 못해 `warning` 으로 접은 것일 수도 있고, 그때 "일부 중단" 이라고 하면 바로 옆의 `4/4` 와 모순된다. 개수가 전부 동작이면 `CI 러너 주의` / `위험` 처럼 레벨만 말한다. 원인 우선순위는 전원 > 디스크 > 러너 (동률일 때) — 서버를 멈추는 신호가 먼저다.
  - **메뉴바 폭·세로 스택 두 줄 한도에 걸리지 않는 이유.** #31 이 세로 스택 두 줄을 다 썼지만, 러너는 새 줄을 만들지 않는다. 같은 서버의 신호로서 서버 점의 종합 판정에 합쳐지고, 개수는 팝오버에만 나온다. 메뉴바 아이콘은 바뀌지 않는다.
  - **Admission Criteria 통과 근거** ([PHILOSOPHY.md](PHILOSOPHY.md) § Admission Criteria).
    1. 왕복이 실재한다 — PR CI 가 시작하지 않을 때마다 서버에 접속해 러너 상태를 확인하러 가고 있다.
    2. 행동을 부른다 — 러너가 멈추면 서버에서 다시 띄우거나 원인을 봐야 하고, 14일을 넘기면 재등록 비용이 생긴다.
    3. 판정으로 접힌다 — 전부/일부/0 이 ok/warning/critical 로 그대로 접힌다. 이력이 필요 없다.
    4. 메뉴바 폭을 늘리지 않는다 — 위와 같이 서버 점에 합쳐진다. 러너는 별도 대상이 아니라 서버라는 대상의 신호로 센다 — 같은 서버 위에서 같은 원인(꺼짐·잠자기)을 공유하고, 별도 점은 #31 의 두 줄 한도를 넘기 때문이다.
    5. 서버 밖으로 나가도 되는 값이다 — 개수 둘과 레벨 이름뿐이다. 러너 레이블·실행 사용자(`ghrunner`)·설치 경로·조직 이름은 싣지 않으며, `host` 아래 문자열이 세 레벨 이름뿐임을 에이전트 테스트가 러너를 포함한 신호 조합 6가지로 확인한다. 러너의 존재와 대수·가동 상태가 토큰 URL 소지자에게 공개되는 것은 수용한 노출이다 (유출 시 #25 의 토큰 교체).
    - PHILOSOPHY Out of Scope 와의 관계 — "범용 시스템 모니터" 와 "다중 모니터링" 항목이 서버에 대해 "곧 멈출 조짐" 만, 서비스는 하나도 더하지 않는 것처럼 읽혀, 이 결정과 함께 좁혔다: 사용률 지표와 여러 서버·임의로 늘려 가는 범용 서비스 모니터링은 여전히 범위 밖이고, 서버 한 대 위의 서비스 건강은 Admission Criteria 를 통과한 것만 받는다 (In Scope "곁들이는 상태" 와 같은 문구).
- **결과**:
  - 서버가 러너 신호를 보내지 않으면(구버전 에이전트, 러너 없는 서버, launchctl 을 듣지 못함·러너 마감 초과) 팝오버의 러너 줄은 자리 없이 빠진다 (원칙 2).
  - launchctl 을 듣지 못하거나 러너 마감을 넘긴 주기에는 러너가 서버 점 종합 판정에서 빠져, 러너가 전부 죽은 서버도 그 주기 동안 점이 초록일 수 있다.
  - 관대한 읽기 — `host.runners` 가 객체가 아니면 없음. `running`·`total` 은 0 이상 정수만 받고, `total == 0` 이거나 `running > total` 이면 신호 없음. `health` 누락·모르는 값·문자열이 아닌 값은 `warning` (#31 규칙과 같음). `host.health` 가 없을 때의 "가장 나쁜 신호" 에 러너가 들어간다.
  - 알림 — #31 의 신호별 규칙(기준점·상승 시 알림·쿨다운·미룸·게이트)을 세 번째 신호로 그대로 따른다. 식별자 `server-host-runners`, 제목 `서버 CI 러너 일부 중단` / `서버 CI 러너 전부 중단`, 본문 `4대 중 3대 동작`.
  - 에이전트 로그의 `호스트:` 줄 비교 키에 러너 레벨이 들어간다.
  - 러너 설치 스크립트는 조직 저장소 [mongshell-io/server-mac](https://github.com/mongshell-io/server-mac) 의 `ci-runner/` 가 소유한다 (gambau 에서 옮겨 옴). LaunchDaemon 레이블 접두사 `com.github.actions-runner.` 와 plist 위치 `/Library/LaunchDaemons/` 는 그 스크립트가 정하고 이 에이전트가 읽는 약속이라, 한쪽을 바꾸면 다른 쪽도 함께 바꾼다.
  - 배포 순서 — #31 과 같다. 서버를 먼저 올려도 구버전 앱은 `runners` 를 무시하고(서버 점의 색은 종합 판정이라 러너가 반영된다), 앱을 먼저 올리면 러너 줄이 보이지 않을 뿐이다.
- **트레이드오프**:
  - 프로세스가 떠 있어도 GitHub 과의 연결이 끊긴 상태(네트워크·토큰 문제로 offline)는 보지 못한다. launchd 가 보는 것은 프로세스뿐이다.
  - 14일 미연결로 GitHub 이 등록을 지운 러너도 보지 못한다 — 프로세스는 계속 떠서 재연결을 시도할 수 있고, plist 도 남아 있다.
  - 러너가 잡을 돌리는 중(busy)인지는 모른다. 판정에 쓰이지 않으므로 싣지 않는다.
  - 레이블 하나라도 launchctl 응답을 받지 못하면 나머지 러너의 상태도 함께 버린다. 부분 결과로 `total` 이 줄어든 것처럼 보이게 하는 것보다 낫다고 봤다.
  - 러너마다 `launchctl` 을 한 번씩 부른다(레이블당 5초 타임아웃). 러너 4개면 매 주기 4번의 짧은 셸아웃이 더해진다.
  - 러너 자동 재시작은 범위 밖이다 — LaunchDaemon `KeepAlive` 가 이미 한다. 에이전트는 사용자 권한이라 system 도메인의 서비스를 kickstart 할 수도 없다.
- **폐기 조건**: GitHub 연결 상태(online/offline)가 필요해지거나, 러너가 서버 맥 밖(다른 머신·클라우드)으로 옮겨 가면 이 방식은 맞지 않는다 — 그때는 B안을 권한 범위와 함께 다시 따진다.

## Decision #79: probe 시간 초과는 따로 판정하고, 시간 초과만으로는 늦게 재시작한다

- **도입**: 미정 (#79)
- **컨텍스트**: 2026-10-24 서버 맥 load average 23~47(Chrome 수집 배치 + CI 러너 4개)에서 에이전트가 하루 7번 probe 시간 초과로 down 을 판정했고, 그중 두 번은 연속 2회 규칙으로 살아 있는 게이트웨이를 kickstart 해 진행 중이던 작업을 끊었다. 같은 순간 게이트웨이는 `channels.status` 에 720ms 로 답했다 — 8초는 `openclaw` CLI(node) 콜드 스타트까지 포함한 시간이라, 부하가 높으면 CLI 를 띄우는 것만으로 넘는다.
- **결정**:
  - `Probe.probeTimeout` 8초 → 25초. 주기 하한(`--interval`, 에이전트·`server/lib.sh`)은 15초 → 30초 — probe 한 번이 최대 27초라서.
  - 시간 초과를 `ProbeVerdict.timedOut` 으로 따로 판정한다. 상태 문서에는 `health: down` + `detail: "응답 지연 · 25초 초과"` 로 싣는다 — 앱은 이미 down 의 detail 을 보여 주므로 앱·스키마 변경이 없다.
  - 자동복구: 연속 실패에 시간 초과가 아닌 실패(down·degraded)가 하나라도 있으면 기존처럼 2회, 시간 초과만 이어졌으면 4회에서 재시작한다. 쿨다운 600초는 그대로다.
  - 복구 직후(3초 뒤) 재확인의 실패는 시간 초과처럼 약하게 센다 — 게이트웨이가 아직 뜨는 중이라 "not reachable" 이 나오기 쉬운데, 이를 확실한 실패로 세면 주기가 길 때(300초 초과) 쿨다운 뒤 시간 초과 한 번만으로 다시 재시작한다.
- **이유**:
  - 시간 초과만으로는 "게이트웨이가 멈춤" 과 "서버가 바빠 CLI 가 늦게 뜸" 을 가를 수 없다. 반면 연결 거부·not reachable 은 게이트웨이가 확실히 없다는 응답이라 빨리 고칠 가치가 있다. 그래서 횟수만 다르게 세고, 시간 초과도 결국은 고친다 — openclaw 의 longpoll 멈춤은 매번 시간 초과로 보이므로, 이를 아예 복구에서 빼면 원래 자동복구를 둔 이유가 사라진다.
  - 녹색/빨강 사이의 새 상태(예: 앱의 "응답 지연" 노랑)는 만들지 않았다. 시간 초과가 이어지면 실제로 게이트웨이가 멈춘 것일 수 있어 빨강이 맞고, 원인은 detail 로 충분히 구분된다.
- **결과**:
  - 실제 멈춤의 복구가 늦어진다 — 시간 초과만 이어지면 첫 시간 초과부터 3주기(기본 60초 주기 + probe 최대 27초 → 약 4~5분) 뒤에 재시작한다.
  - 저장된 `interval` 이 15~29 인 서버는 다음 `install.sh` 때 경고 후 기본값(60)으로 간다. 에이전트 인자로 직접 넘긴 값은 30 으로 올린다.
- **트레이드오프**:
  - 이슈가 선택지로 든 게이트웨이 HTTP/WS 헬스 엔드포인트 직접 확인(CLI 콜드 스타트 제거)은 하지 않았다. 엔드포인트 사양이 문서화돼 있지 않고, 채널 상태는 여전히 CLI 로만 얻을 수 있어 경로가 둘이 된다. 부하 때 오판정이 계속되면 다시 본다.

## Decision #81: 서버 에이전트 버전을 git 에서 찍어 상태 문서와 팝오버에 싣는다

- **도입**: 미정 (#81)
- **컨텍스트**: 에이전트에는 버전이 어디에도 없었다 — 바이너리·로그·`status.json` 모두. 서버 맥은 `git pull && server/install.sh` 로 main 을 그대로 빌드하므로, 지금 어떤 빌드가 떠 있는지, `git pull` 만 하고 `install.sh` 를 돌리지 않았는지를 맥북에서 알 수 없었다. #79 처럼 판정 규칙을 바꾼 뒤에는 그 변경이 실제로 서버에 올라갔는지가 곧 궁금해진다.
- **결정**:
  - `install.sh` 가 빌드할 소스에서 `git describe --tags --match 'v[0-9]*' --long` 으로 버전을 정한다. 릴리스 tag 위면 `v1.2.0`, 그 뒤로 커밋이 N개면 `v1.2.0+N`. 그 값을 LaunchAgent 인자 `--build-version` 으로 넘긴다.
  - 에이전트는 시작 로그(`시작 — version=…`)에 찍고, `[0-9A-Za-z.+-]` 1–32자일 때만 상태 문서 최상위 `agentVersion` 에 싣는다 (아니면 `null`). `schema` 는 1 그대로다 (키 추가 — #31 과 같은 이유).
  - 앱은 관대하게 읽어(문자열만, 한 줄로 펴고 32자 상한) 팝오버 "서버 확인" 시각 아래에 `에이전트 v1.2.0+3` 으로 보인다. 값이 없으면 줄을 그리지 않는다 (원칙 2). 메뉴바·hover 에는 넣지 않는다.
- **이유**:
  - **`v1.2.0+N` 형식.** tag 만(`v1.2.0`) 쓰면 릴리스 사이의 커밋이 모두 같은 버전으로 보여 "올라갔는가" 에 답하지 못한다. 커밋 수를 마지막 자리에 더해(`v1.2.3`) 만들면 나중의 실제 릴리스 번호와 겹친다. `git describe` 기본형(`v1.2.0-3-gabc1234`)은 정확하지만 길다. `+N` 은 tag 의 순서를 지키면서 커밋이 하나 늘 때마다 반드시 바뀌고, 앱 버전(#47, tag 만)과 섞여도 혼동되지 않는다. 같은 main 위에서는 N 이 단조 증가하므로 해시 없이도 구분된다.
  - **배포를 릴리스 tag 에 묶지 않는다.** 서버가 최신 tag 만 설치하면 표시는 늘 `v1.2.0` 처럼 깔끔하지만, 에이전트 수정을 올릴 때마다 `/release` 가 필요해진다. 지금의 `git pull && install.sh` 흐름을 유지한다.
  - **버전 주입을 바이너리가 아니라 실행 인자로.** 에이전트는 Info.plist 가 없는 맨 실행 파일이고, 소스 파일을 빌드 전에 고쳐 쓰면 추적 파일이 더러워져 다음 `git pull` 과 부딪힌다. `install.sh` 가 같은 소스를 빌드하고 같은 plist 를 쓰므로 인자의 값이 실행 중인 바이너리와 어긋날 경로가 없다. 손으로 띄운 바이너리는 버전이 없다(`null`) — 거짓 값보다 낫다.
  - **공개 문서에 버전을 싣는 것.** 상태 문서는 "기계를 식별하는 것(호스트명·경로·버전)은 싣지 않는다" 를 원칙으로 했다 (#25, [PHILOSOPHY.md](PHILOSOPHY.md) Admission Criteria 5). 이 결정과 함께 기준 5 의 "버전" 을 서버 소프트웨어(openclaw·OS) 버전으로 좁혔다. 이 버전은 공개 저장소의 커밋 위치일 뿐이라 토큰 URL 소지자가 새로 알게 되는 것은 "이 서버가 어느 커밋의 에이전트를 돌리는가" 정도다. openclaw·OS 버전처럼 서버의 소프트웨어 구성을 드러내는 값은 여전히 싣지 않는다. 앱이 서버의 다른 판정과 같은 문서·같은 경로로 받으므로 새 네트워크 경로·자격증명이 없다.
  - **Admission Criteria 의 대상이 아니다.** 버전은 서버의 상태를 알리는 신호가 아니라 상태 문서를 쓴 쪽에 대한 메타데이터다 — 판정으로 접히지 않고(기준 3) 행동을 부르지도 않지만(기준 2), "서버 확인" 시각처럼 받은 문서를 해석하는 데 쓰는 값이다. 노출 문제인 기준 5 만 위 항목으로 다룬다.
  - **표시 위치.** 버전은 확인할 때만 보는 값이라 PHILOSOPHY 원칙 1(메뉴바 폭)에 걸리지 않게 팝오버에만 둔다. "서버 확인" 시각 옆이 아니라 아래 줄인 이유 — 두절 때 시각에 경과(`· 23분 전`)가 붙으면 새로고침 버튼과 겹친다.
- **결과**:
  - 커밋 안 된 작업 트리 수정은 버전에 반영되지 않는다. 서버 맥에서 직접 고친 코드는 같은 버전으로 보인다.
  - 클론에 `v*` tag 가 없으면(얕은 클론 등) `install.sh` 가 경고하고 버전 없이 설치한다.
  - 배포 순서 — #31 과 같다. 서버를 먼저 올리면 옛 앱은 `agentVersion` 을 무시하고, 앱을 먼저 올리면 버전 줄이 보이지 않을 뿐이다.
- **트레이드오프**:
  - 서로 다른 브랜치에서 같은 tag 뒤 N 번째 커밋은 같은 버전으로 보인다. 서버는 main 만 설치하므로 실제로는 생기지 않는다고 봤다.
